### Task 1: Prepare the spare chip over ticks (retire M1's exception)

**Complete:** `aefb2ab`; measured results below.

**Why first:** with two chips, a profile step on either would hold the main loop for up to
471.5k instructions, four times the poll allowance. Splitting it is a prerequisite for chip
B, and it touches the same code Task 2 does.

**Files:** `app/reg_ring.c`/`.h`, `core/sid/sid.c`/`.h`, `core/sid/sid_filter.c`/`.h`,
`core/sid/sid_character.c`, `app/live.c` (when a reset is sent), tests in
`host/crates/sidou-tests/tests/app/reg_ring.rs` and emu-gate `tests/screen.rs`,
`tests/character.rs`, `tests/common/mod.rs` (`render_host`).

**Spec:**
- **The request, not the reset, is what changes hands.** Today `reg_ring_sink` meets a
  `LIVE_REG_RESET`, waits for the ring to empty and prepares the whole spare in that call.
  Instead: a model or profile change starts a **preparation** of the spare (model,
  profile, the character's settings), and only when the spare is whole does live send
  `LIVE_REG_RESET` and the registers after it, exactly as today. Until then the old chip
  keeps playing, unchanged: no gap, no click beyond today's swap.
- **One slice per `live_tick`, and only there:** `reg_ring_prepare_step` does one slice of
  the work, called once from each `live_tick` (every 10 ms), never from elsewhere in the
  pass. So the number of ticks a preparation takes is a function of the request alone
  (model, profile, character), and the tick on which the reset is sent, and so the block
  the swap lands in, is the same on the host and on the device: the host's `render_host`
  steps the preparation per tick the same way, which keeps the bit-exact tests exact.
- **The slice:** at most **`REG_RING_PREPARE_SLICE` = 40,000 instructions** (measured on
  the device, gated in the emu). Why 40,000: the busiest frame's pass is `LIVE_WORST_POLL`
  (68,000) on LIVE, `CHIP_PASS` (49,000) on CHIP; 68,000 + 40,000 = 108,000 leaves 12,000
  of the 120,000 allowance for MIDI's drain. A pass that runs a slice sets a flag the
  store's poll reads (M2a Task 4: it skips that pass, so a slice and the store's 30,000
  never share one); if M2a Task 4 is not in yet, add the flag and leave a comment. The pieces to split (0006's measurements):
  `sid_init` (~0.16 M: its table builds, each in ≤ 40k pieces), the filter's two rows
  (~0.23 M: a row built a range of its entries at a time), the DAC table (~0.08 M: two
  pieces). About **12-13 slices**, so a profile step takes about 120-130 ms (report the
  exact count per profile); the step's toast covers it.
- **Requests that arrive while one is preparing** coalesce: the newest wins, the
  preparation restarts (or continues, if the model and profile are the same and only the
  character differs).
- The host sink (`live_sid_sink`) may still apply everything at once where a host test does
  not care about ticks, but the staged build must give bit-identical tables to the one-shot
  build (test), and `render_host` (the emu's host comparison) uses the per-tick path.

**Tests:**
- host: the staged build equals the one-shot build, table for table, for every profile and
  model at several character settings; the slice count is the same on every run for a
  request; a request during a preparation; coalescing; the ring's invariants (nothing is
  lost, the reset still waits for nothing it needs);
- fm1-emu: `CHIP_RESET_PASS` and `CHIP_PROFILE_PASS` (`tests/screen.rs`) tighten from 520k
  to `POLL_INSTRUCTIONS` (120k): the CHIP view's ALGORITHM, CC 85 and the FX button onto
  worn at full character, every pass within the allowance; each slice ≤ 40,000
  (`REG_RING_PREPARE_SLICE`, a new constant beside them) and every pass with a slice and the
  view's busiest frame ≤ 120,000; the latency gate (`latency.rs`) with a profile step in
  flight passes its normal bound (no more 5 ms exception); the swap's audio is bit-exact
  with the host build doing the same, swap block included (as `character.rs`).

**Docs:** decision record 0006 (an amendment to "Cost": the exception is gone, the slice and
the tick count), `docs/TODO.md` (remove the entry), `CHANGELOG.md`.

**Commit:** `perf(reg_ring): prepare the spare chip a slice a tick; no main-loop pass over the allowance`

### Task 2: Two chips in the ring

**Complete:** `0a9b15f`; shared spare/build table and measured POOL cost below.

**Files:** `app/reg_ring.c`/`.h`, `app/live.c`/`.h` (the sink's chip), `app/fx_live.c`,
tests.

**Spec:**
- **Entries carry their chip.** The entry stays two bytes. A SID register for chip A is
  `0x00..0x18` as today, for chip B `0x40..0x58`; chip B's chip pseudo-registers mirror
  A's at `0xC0..0xC8` (reset, gate reset, character fields, character tick,
  `REG_RING_CHARACTER`); the slots' pseudo-registers `0xA0..0xB7` stay chip-less (one effect
  chain on the mix, overview decision 7). Check no other code uses `0x40..0x58` or
  `0xC0..0xC8` today, and assert the ranges with `_Static_assert`s.
- **One ring, both chips,** so a pass's writes to A and B stay in order with each other.
  `REG_RING_WORST_PASS` (391) is recomputed for two chips (the instrument on one, M2c's song
  control on A, MIDI) and `REG_RING_SIZE` (1,024) grows if needed (each entry 2 bytes).
- **`reg_ring_chips` holds three `sid`s:** chip A, chip B and **one spare** both share
  (only one preparation runs at a time; a request for the other chip waits for it, at most
  about 13 ticks after Task 1). The drain swaps the spare with whichever chip the reset
  names. Each logical chip keeps its own character ramp and its two stages.
- **The DAC tables, decided: A and B share one build table.** Each chip keeps the table it
  plays (17,408 bytes each); a **third table** is the one a ramp builds into, used by one
  chip at a time: a ramp on A and a ramp on B cannot build at once, so a character change on
  one chip while the other's ramp builds waits for it (at most the ramp's length, 0.32 s end
  to end, 0006). Saves 17,408 bytes against a pair a chip, which M3's RAM needs (overview,
  RAM). Record the measured POOL figure in this plan's results and in the overview.
- **The sinks:** `reg_ring_sink` takes the chip from a context (`reg_ring_out` gets a chip
  field), so the instrument writes through a sink bound to the chip the keys play (Task 4)
  and M2c's song control through one bound to chip A. Live itself stays chip-agnostic: it
  writes `0x00..0x18` and its sink adds the chip.

**Tests (host):** every pseudo-register for each chip reaches that chip; A's and B's writes
interleaved in one pass apply in order; a reset of A while B plays leaves B untouched, bit
for bit; the shared spare serialises two requests; the shared build table serialises two
ramps (the second starts when the first ends, and both end at their targets); the worst
pass for two chips fits without waiting; the existing ring tests pass with chip A only.

**Commit:** `feat(reg_ring): two chips in one ring, one shared spare and one shared build table`

### Task 3: Render and mix both chips on the device

**Complete:** `487707a`; two-chip ISR, fade and headroom results below.

**Files:** `platform/fm1/audio.c`/`.h`, `app/scope.c`/`.h` (which chip the tap reads),
`platform/fm1/app.ld` (if a new function needs `.ram_text`), emu-gate tests,
`tests/common/mod.rs` (`render_host`).

**Spec:**
- **Chip B's sid exists only after its first reset** (from Task 2, app/reg_ring.h): until
  then `chip[1]` is zeroed (its sample rate 0). Its first reset happens at boot only,
  **prepared** in the background a slice a pass from the main loop's first ticks (during the
  boot's title card), then sent (Task 3's `audio_chip_b_boot`; from Task 4 chip B's
  `chip_ctl` following the keys' setup). Never render
  chip B before that reset. (Done in Task 3: an unprepared reset before the main loop, 0.5 M
  instructions, moved the boot's timeline, and with it three LCD goldens, LIVE's busiest
  ui_poll and a title card's SPI frame, as the 8580's default DACs built at boot had in Task
  1.)
- **Chip B renders only while it is in use.** A silent chip does not output 0: its voices'
  DC, the thump offsets and its external filter's settling give it a level of its own. So
  `audio_fill` renders chip B only while it is **in use**: the keys play it (Task 4), a UI
  sound plays on it (Task 7), or (M5) a song track does. Out of use, it is not rendered and
  adds nothing. Going in and out of use happens at a block boundary, and chip B's
  contribution fades in or out linearly over that one block (128 samples), so its DC step
  never clicks. The fade is in integer arithmetic, so the host matches it bit for bit.
- With chip B out of use, **the output is chip A's, bit for bit**, so every existing golden
  and host comparison holds unchanged (none of M1's scenarios puts chip B in use).
- In use, `audio_fill` renders chip A and chip B into two 128-sample buffers and mixes them
  before the slots: `sat16(a + b)`. Document the headroom: two full-scale chips clip at the
  mix; the SID's own output peaks well under full scale (measure the worst two-chip peak on
  the golden scenarios and record it).
- The LIVE view's tap follows the chip the keys play (Task 4), chosen at a block boundary.
- Chip B's setup at power-on is the keys' setup (Task 4): M1's default, the 6581 R4AR, or
  what the settings say.

**Tests (fm1-emu):**
- **The real interrupt with two chips:** a new test drives both chips at their worst (the
  noise-combined power-on transient, `noise_tri_ring_0800`, on A and B, both in use) with
  every slot at its heaviest and measures the device's own worst block, **against 2,700 a
  sample** (`AUDIO_TARGET`), and its share above the gates' sum (the mix, the second call,
  the fade): expected under 10 a sample. Record the 6502's remaining headroom (expected
  about 200 of 205).
- Chip B out of use: every existing golden and `character.rs`/`fx_live.rs` comparison
  unchanged, bit for bit; the interrupt's cost with chip B out of use equals M1's within
  1 a sample.
- In and out of use: the fade's block bit-exact with the host; no step above a quarter of
  the DC level in any sample (a click test).
- The host and device outputs bit-exact with both chips playing (the host renders A, B,
  fades, mixes and runs the slots as `audio_fill` does: extend `render_host`).
- `ram_audio.rs`: still only `.ram_text` in the interrupt; report RAMTEXT.
- `slots_budget.rs`, `fx_live.rs`, `character.rs`, `latency.rs` pass unchanged or with
  bounds tightened.

**Docs:** `docs/hardware.md` (the audio path with two chips, chip B's use; RAMTEXT),
decision record 0004 ("Worst blocks": the device's two-chip block), `docs/TODO.md` (the
6502's headroom figure), `CHANGELOG.md`.

**Commit:** `feat(fm1): chip B renders beside chip A while in use, mixed before the slots`

### Task 4: Which chip the keys play; `chip_ctl` per chip

**Complete:** `e45bd48`; settings now persist through the integrated M2a record.

**Files:** `app/live.c`/`.h`, a new `app/chip_ctl.h`/`.c` (below), `app/keys_route.h`/`.c`
(new: which chip the keys play), `app/panel.c`, `app/views.c`, `app/live_view.c`,
`app/midi_map.c`, `app/settings.c` (KEYS, a migration), `platform/fm1/main.c`,
`platform/fm1/midi.c`, tests.

**From the review of Tasks 1-2, binding here:**
- Chip B's first reset is a boot preparation (Task 3; in Task 4 `chip_ctl` following the
  keys' setup from the first ticks), never an
  unprepared reset: no `live_init` or other reset made at once on B at runtime (it would
  hold the main loop for 0.5 M instructions). Every change of B's setup goes through the
  preparer, a slice a pass.
- A preparation for one chip that waits for the other's (the spare is shared) holds the other
  chip's ramp from starting new DAC tables (`prep_wait`, reg_ring.c); keep that when the keys
  move between chips, and test that neither chip's request starves. (Done in Task 4 as the
  keys' chip first, `reg_ring_set_keys`: the keys' chip never waits for the other, which
  catches up when the keys' chip is quiet; tests in sidou-tests' reg_ring.rs.)

**The rule (the user's decision, 2026-10-16):**
- **No song playing: the keys play chip A,** exactly as in M1 (the same chip, the same
  setup, the same sound, every existing test unchanged).
- **A song playing on chip A** (M2c's transport running): **the keys play chip B.**
- **The KEYS setting** (menu, persisted): **AUTO** (the default, the two lines above) or
  **A**: the keys play chip A even while a song plays. Then a key takes a voice from the
  song while it sounds (the song's writes to that voice are held back, as M2c's mute does,
  and given back at the key's release), the song keeps the filter and the volume
  (`$D415-$D418`; the instrument's filter knobs do nothing while the song plays), and the
  keys sound through the song's chip setup (one chip has one setup). Until M2c, "a song
  playing" is a test hook that is never set on the device.

**The model mismatch, resolved: the keys' setup travels with the keys.** The instrument owns
one chip setup, **the keys' setup** (model, profile, the four character controls, the
expert values from Task 6): M1's 6581 R4AR by default, or what the settings say. It is
applied to the chip the keys play, so moving the keys never changes their sound:
- **Chip B always holds the keys' setup.** It starts with it (not the 8580 R5), and every
  change to the keys' setup is prepared on chip B too, in the background (Task 1's
  preparation, after any preparation of the chip the keys play), so chip B is ready
  whenever the keys move to it.
- With no song playing, chip A holds the keys' setup too (the keys play it). When a song
  starts, chip A takes the song's setup (its `CHPA` chunk, M2c) if it has one; the
  transport starts once chip A's preparation is done (at most about 13 ticks; none if the
  song has no `CHPA` or it equals the keys' setup). When the song stops, chip A is prepared
  back to the keys' setup, and the keys stay on chip B (the same sound) until it is ready
  **and** no key is held; then they return to chip A.
- **Held keys at a move:** when a song starts, notes the keys hold on chip A are released
  there (the song takes the chip) and the keys still down sound again on chip B; when the
  keys return to A they move only with no key held, and chip B stays in use until its
  envelopes are at 0, so the release tails play out on it (amended after review: the move
  itself comes one tick after the last key-up; nothing is cut and nothing of chip B is left
  frozen for later).
- The CHIP view's tabs (Task 5) show chip A and chip B; the tab the keys play is marked
  `KEYS`. Editing the keys' tab edits the keys' setup (and so both chips while no song
  plays); editing chip A while a song plays edits the song's setup (its `CHPA`, saved with
  the song).

**What moves out of live:** the model, profile and character handling (requests, the
coalesced apply at `live_tick`, the ramp's settings, the FX toggle's memory of the last
6581 profile) becomes `chip_ctl`, one per chip. `live` keeps the instrument (voices,
presets, knobs, expression) and writes through the sink `keys_route` binds to the keys'
chip; chip A's `chip_ctl` has no voices of its own: while a song plays its registers come
from M2c's player. Behaviour with no song is exactly M1's (all existing live tests pass
unchanged).

**MIDI in M2b:** everything M1 routes (notes, the CC map, NRPN, learn, expression) goes to
the instrument, so to the chip the keys play. Chip-level CCs (CC 25 model, CC 85 profile,
86-90 character) act on the keys' setup. M2e adds addressing chip A from MIDI.

**Views:** LIVE shows the keys' chip (its voices, its envelopes, its filter) and says
`KEYS: B` in its status line while they play chip B (written `KEYS:B`, without the space:
the header's width); the status screen shows both chips'
models and profiles; the boot banner says `CHIP A + CHIP B  6 VOICES` (as the prototype's
boot did).

**Tests:** host: the live tests pass unchanged with no song; `chip_ctl` round trips; with
the song hook set, keys sound on B, and a key held across the start re-sounds on B; at
stop the keys stay on B until A is ready and no key is held; KEYS A with the hook set
takes a voice and gives it back; chip B's setup equals the keys' after any change (its
background preparation); fm1-emu: a key sounds from chip A with no song (chip B out of use,
the audio bit-exact with M1's goldens); with the hook set, a key sounds from chip B with
the same samples as from A (same setup, the chip's own output compared before the mix);
the FX button and the CHIP view's profile act on the keys' setup; LCD goldens for LIVE and
STATUS updated (with the reason).

**Docs:** `docs/reference/controls.md` (KEYS, which chip the panel plays), `docs/reference/
midi.md` (generated: which chip the CCs reach), `CHANGELOG.md`.
