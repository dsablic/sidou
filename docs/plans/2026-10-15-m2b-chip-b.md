### Task 1: Prepare the spare chip over ticks (retire M1's exception)

**Why first:** with two chips, a profile step on either would hold the main loop for up to
471.5k instructions, four times the poll allowance. Splitting it is a prerequisite for chip
B, and it touches the same code Task 2 does.

**Files:** `app/reg_ring.c`/`.h`, `core/sid/sid.c`/`.h`, `core/sid/sid_filter.c`/`.h`,
`core/sid/sid_character.c`, `app/live.c` (when a reset is sent), tests in
`host/crates/sidou-tests/tests/app/reg_ring.rs` and emu-gate `tests/screen.rs`,
`tests/character.rs`.

**Spec:**
- **The request, not the reset, is what changes hands.** Today `reg_ring_sink` meets a
  `LIVE_REG_RESET`, waits for the ring to empty and prepares the whole spare in that call.
  Instead: a model or profile change starts a **preparation** of the spare (model,
  profile, the character's settings) that `reg_ring_prepare_step` advances by at most
  `REG_RING_PREPARE_SLICE` instructions' worth of work per call (one call per tick from
  `live_tick`, or per main-loop pass), and only when the spare is whole does live send
  `LIVE_REG_RESET` and the registers after it, exactly as today. Until then the old chip
  keeps playing, unchanged: no gap, no click beyond today's swap.
- **The pieces to split** (0006's measurements): `sid_init` (~0.16 M: split into its table
  builds), the filter's two rows (~0.23 M: build a row in chunks of its entries), the DAC
  table (already in four stages). Target: no step above ~90k instructions, so a pass with a
  step, MIDI and a frame stays inside 120k.
- **Requests that arrive while one is preparing** coalesce: the newest wins, the
  preparation restarts (or continues, if the model and profile are the same and only the
  character differs).
- The host sink (`live_sid_sink`) keeps applying everything at once (the host tests do not
  care about passes), but the device path and the host must still make the same chip: the
  staged build must give bit-identical tables to the one-shot build (test).

**Tests:**
- host: the staged build equals the one-shot build, table for table, for every profile and
  model at several character settings; a request during a preparation; coalescing; the
  ring's invariants (nothing is lost, the reset still waits for nothing it needs);
- fm1-emu: `CHIP_RESET_PASS` and `CHIP_PROFILE_PASS` (`tests/screen.rs`) tighten from 520k
  to `POLL_INSTRUCTIONS` (120k): the CHIP view's ALGORITHM, CC 85 and the FX button onto
  worn at full character, every pass within the allowance; the latency gate
  (`latency.rs`) with a profile step in flight passes its normal bound (no more 5 ms
  exception); the swap's audio is bit-exact with the host build doing the same (as
  `character.rs`); how many ticks a profile step now takes (report it: expected 6-10, about
  60-100 ms, which the title of the step's toast hides).

**Docs:** decision record 0006 (an amendment to "Cost": the exception is gone, with the
numbers), `docs/TODO.md` (remove the entry), `CHANGELOG.md`.

**Commit:** `perf(reg_ring): prepare the spare chip over ticks; no main-loop pass over the allowance`

### Task 2: Two chips in the ring

**Files:** `app/reg_ring.c`/`.h`, `app/live.c`/`.h` (the sink's chip), `app/fx_live.c`,
tests.

**Spec:**
- **Entries carry their chip.** The entry stays two bytes. A SID register for chip A is
  `0x00..0x18` as today, for chip B `0x40..0x58`; chip B's chip pseudo-registers mirror
  A's at `0xC0..0xC8` (reset, gate reset, character fields, character tick,
  `REG_RING_CHARACTER`); the slots' pseudo-registers `0xA0..0xB7` stay chip-less (one effect
  chain on the mix, overview decision 7). Check no other code uses `0x40..0x58` or
  `0xC0..0xC8` today, and assert the ranges with `_Static_assert`s.
- **One ring, both chips,** so a pass's writes to A and B stay in order with each other.
  `REG_RING_WORST_PASS` (391) is recomputed for two chips (live on B, M2c's song control
  on A, MIDI) and `REG_RING_SIZE` grows if needed (each entry 2 bytes).
- **`reg_ring_chips` holds three `sid`s:** chip A, chip B and **one spare** both share
  (only one preparation runs at a time; a request for the other chip waits for it, at most
  a few ticks after Task 1). The drain swaps the spare with whichever chip the reset names.
  Each logical chip keeps its own character ramp, its two stages and its DAC tables.
- **The DAC tables:** each chip's character builds into one of two tables (2 × 17,408 bytes
  a chip). Measure POOL with both chips' pairs. If POOL keeps less than the overview's
  margin, share one build table between A and B (a chip's ramp builds only when the other's
  is not building), saving 17,408 bytes; record the choice and the figures in this plan's
  results and in the overview.
- **The sinks:** `reg_ring_sink` takes the chip from a context (`reg_ring_out` gets a chip
  field), so live writes through a sink bound to chip B and M2c's song control through one
  bound to chip A. Live itself stays chip-agnostic: it writes `0x00..0x18` and its sink
  adds the chip.

**Tests (host):** every pseudo-register for each chip reaches that chip; A's and B's writes
interleaved in one pass apply in order; a reset of A while B plays leaves B untouched, bit
for bit; the shared spare serialises two requests; the worst pass for two chips fits
without waiting; the existing ring tests pass with chip A only.

**Commit:** `feat(reg_ring): two chips in one ring, one shared spare`

### Task 3: Render and mix both chips on the device

**Files:** `platform/fm1/audio.c`/`.h`, `app/scope.c`/`.h` (which chip the tap reads),
`platform/fm1/app.ld` (if a new function needs `.ram_text`), emu-gate tests.

**Spec:**
- `audio_fill` renders chip A and chip B into two 128-sample buffers and mixes them before
  the slots: `sat16(a + b)`. With chip B silent the output is chip A's, bit for bit (and
  the other way round), so every existing golden and host comparison holds with one chip.
  Document the headroom: two full-scale chips clip at the mix; the SID's own output peaks
  well under full scale (measure the worst two-chip peak on the golden scenarios and record
  it).
- The LIVE view's tap follows the chip the keys play (Task 4), chosen at a block boundary.
- Chip B starts at power-on as the 8580 R5 or as settings say (M2a Task 5's record gains
  chip B's fields through a migration; until M2a lands, M1's defaults).

**Tests (fm1-emu):**
- **The real interrupt with two chips:** a new test drives both chips at their worst (the
  noise-combined power-on transient, `noise_tri_ring_0800`, on A and B) with every slot at
  its heaviest and measures the device's own worst block, **against 2,700 a sample**
  (`AUDIO_TARGET`), and its share above the gates' sum (the mix, the second call): expected
  under 10 a sample. Record the 6502's remaining headroom.
- The host and device outputs bit-exact with both chips playing (the host renders A, B,
  mixes and runs the slots as `audio_fill` does: extend `render_host` in
  `tests/common/mod.rs`).
- `ram_audio.rs`: still only `.ram_text` in the interrupt; report RAMTEXT.
- `slots_budget.rs`, `fx_live.rs`, `character.rs`, `latency.rs` pass unchanged or with
  bounds tightened.

**Docs:** `docs/hardware.md` (the audio path with two chips; RAMTEXT), decision record 0004
("Worst blocks": the device's two-chip block), `docs/TODO.md` (the 6502's headroom
figure), `CHANGELOG.md`.

**Commit:** `feat(fm1): chip B renders beside chip A, mixed before the slots`

### Task 4: The keys play chip B; chip A waits for the song

**Files:** `app/live.c`/`.h`, a new `app/chip_ctl.h`/`.c` (below), `app/panel.c`,
`app/views.c`, `app/live_view.c`, `app/midi_map.c`, `platform/fm1/main.c`,
`platform/fm1/midi.c`, tests.

**Spec:**
- **What moves out of live:** the model, profile and character handling (requests, the
  coalesced apply at `live_tick`, the ramp's settings, the FX toggle's memory of the last
  6581 profile) becomes `chip_ctl`, one per chip. `live` keeps the instrument (voices,
  presets, knobs, expression) and owns chip B's `chip_ctl`; chip A's `chip_ctl` has no
  voices: its registers will come from M2c's player. Behaviour for chip B is exactly M1's
  for the one chip (all existing live tests pass, pointed at B).
- **KEYS setting** (open question in the overview; proposed default B): a menu item KEYS
  A/B; with A, the instrument plays chip A as in M1 and chip B is free (for UI sounds and,
  later, M5's chip B tracks). Persisted (M2a's settings, a migration).
- **MIDI in M2b:** everything M1 routes (notes, the CC map, NRPN, learn, expression) goes
  to the instrument, so to the chip the keys play. Chip-level CCs (CC 25 model, CC 85
  profile, 86-90 character) act on that chip. M2e adds addressing chip A from MIDI.
- **Views:** LIVE shows the keys' chip (its voices, its envelopes, its filter); the status
  screen shows both chips' models and profiles; the boot banner says
  `CHIP A + CHIP B  6 VOICES` (as the prototype's boot did).

**Tests:** host: the live tests pass on chip B; `chip_ctl` round trips; KEYS switches the
instrument's chip without a stuck note (notes held across the switch are released on the
old chip); fm1-emu: a key sounds from chip B (A's registers untouched: read both chips'
registers through a test hook or compare the host render); the FX button and the CHIP
view's profile act on B; LCD goldens for LIVE and STATUS updated (with the reason).

**Docs:** `docs/reference/controls.md` (KEYS, which chip the panel plays),
`docs/reference/midi.md` (generated: which chip the CCs reach), `CHANGELOG.md`.

**Commit:** `feat(app): the keys play chip B; chip_ctl per chip`

### Task 6: The character's expert layer

M1c deferred it (decision record 0006, "Not done here"): every analogue parameter as its
own control and NRPN, not only the four macros.

**Files:** `core/sid/sid_character.c`/`.h`, `app/chip_ctl.c`, `app/chip_view.c` (an EXPERT
page), `app/midi_map.c` (NRPN rows 2/5 onwards), `app/settings.c` (user profiles' fields,
a migration), tests.

**Spec:**
- **Inventory first:** list every parameter the character model has (from
  `sid_character.h` and 0006, at least: the 6581 filter curve and range, the 8580 curve,
  the 6581 non-linearity amount, voice-DC bias into the filter, filter bleed, DAC kink and
  leakage, combined-waveform strength, noise write-back, voice DC offsets (thump), the
  external filter's corners), with its range, default per profile, unit and whether it
  needs tables rebuilt. Add the table to decision record 0006 as an amendment.
- **No reset for any expert parameter:** a parameter that needs a table (a filter row, a
  DAC table) builds it over ticks into a free table (Task 1's staging) and swaps it at a
  block boundary as age/heat's stage does; a parameter that is a constant goes through the
  character stage. A held note plays on through every change.
- **The macros stay** and move the expert values along their paths; an expert edit after a
  macro move is kept until the macro moves again (document the rule on the page).
- **The page:** the CHIP view gains EXPERT (the chip focus, EDIT held + ALGORITHM opens it,
  or a fifth SELECT stop; pick what reads best and document it): a scrolling list of the
  chip's parameters, SELECT moves, K1 turns the selected one (coarse), K2 fine; values in
  their units.
- **MIDI:** each parameter an NRPN (MSB 2, LSB from 5 upwards), in the generated map.
- **User profiles** (M2a Task 6) store the expert values too (a schema migration and its
  fixture).

**Tests:** host: each parameter's effect is measurable, monotonic and reaches reSIDfp's
setting at its end points where reSIDfp has one (as 0006's tests do); a jump in any
parameter steps a triangle by at most 1.25 times its own slope (0006's click test); no
gate is lost; fm1-emu: the EXPERT page's goldens, an NRPN changes the sound, every pass
within the poll allowance, the profiles' round trip with expert values.

**Docs:** decision record 0006 (amendment), `docs/reference/controls.md`,
`docs/reference/midi.md` (generated), `CHANGELOG.md`.

**Commit:** `feat(character): the expert layer, every analogue parameter as a control and an NRPN`

### Task 7: UI sounds on chip B's spare voice (M1e Task 6)

**Files:** `app/ui_sound.h`/`.c` (new), `app/live.c` (the voice it may borrow),
`app/views.c` (the triggers), `app/settings.c`, tests.

**Spec:**
- **Sounds:** a cursor blip (menu SELECT), a confirm (a value changed with ALGORITHM, a view
  opened), a toast's chime, the drive "chunk" on SAVE (M2a), an error buzz (a refused
  action). Each is data in **GoatTracker's sound-effect format** (readme section 6.3: AD, SR,
  a pulse byte, then wave/note pairs ending in 0), stepped at 50 Hz (every other
  `live_tick`), which keeps them in the project's song vocabulary and makes them easy to
  edit in GoatTracker and convert.
- **Never steals:** a sound plays on a voice of chip B that is free: its gate off and its
  release run out (from live's voice state and the release time), and not the voice a note
  will need next (live's allocator skips a voice a UI sound holds; if a note comes and all
  three are busy, the UI sound stops and gives the voice up at once). With KEYS on A, chip B
  is all free. Never on chip A, never while a song plays on B (M5).
- **Off by default.** Menu item SOUNDS ON/OFF; persisted (settings migration).
- No filter routing for the borrowed voice (`$d417` bit off for it), and its writes go
  through chip B's sink like live's.

**Tests:** host: the sfx stepper against the format (each step's registers); a chord of
three notes held while the menu is used: no sound, no voice touched; a note while a sound
plays takes the voice back; off means no writes at all; fm1-emu: with SOUNDS on and nothing
held, a menu move sounds (energy in the blip's band), with three notes held it does not
(and the notes are bit-exact with a run without UI sounds); the audio budget unchanged
(they are register writes from the main loop).

**Docs:** `docs/reference/controls.md` (SOUNDS), `docs/art/README.md` (a "UI sounds"
paragraph), the M1e plan's Task 6 marked done here, `CHANGELOG.md`.

**Commit:** `feat(app): UI sounds on chip B's spare voice, off by default`

## Risks and open questions

- **POOL:** chip B costs about 52.7 KB (35.3 KB with a shared DAC table); the overview's
  M3 note depends on the choice made in Task 2.
- **KEYS default B:** the keys sound as in M1, from the other chip, but the CHIP view's A
  tab then edits the song's chip, not the one the keys play; to confirm.
- **Mix headroom:** two loud chips can clip at the mix; measured in Task 3. If the worst
  case clips audibly, mix at -3 dB (a shift and add) and say so (then chip A alone is no
  longer bit-exact with M1: the goldens move, deliberately, with the reason).
- **Two chips at 240 MHz on the device** are unmeasured on hardware (overview, hardware
  flags).
- **Design section 7's per-chip effect slots** are not done (overview decision 7).
