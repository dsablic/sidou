# M2a: Storage, implementation plan

<!-- REUSE-IgnoreStart -->

> **For Claude:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development
> to implement this plan task by task.

**Goal:** SIDOU keeps what the player sets, across power cycles and firmware updates:
settings, MIDI learn's map, the CARDS option, the "full boot once after an install" flag,
user chip profiles, and (for M2c) song files. In a log-structured store in the free flash
region, safe against power loss at any instant, without audible glitches during play, and
never in the way of the update protocol.

**Overview and budgets:** [2026-10-15-m2-overview.md](2026-10-15-m2-overview.md). This plan
needs nothing from the other M2 plans; M2c Task 8, M2d and M2e build on it.

**Background to read first:**
- `docs/hardware.md` ("Code in SRAM", "Updates and recovery"), `platform/fm1/hal/fm1_flash.h`
  (Felucca's RAM flash driver: `fl_erase4k_ram`, `fl_prog_ram`, `fl_read_ram`,
  `fl_plain_window_init`, the `FL_RANGE_OK` gate, Felucca's own ranges `FL_DATA_LO/HI`),
  `platform/fm1/ota_flash.h` (the update protocol's hooks: writes refused while the audio
  runs), `platform/fm1/midi.c` (where `FL_RANGE_OK` is set to the OTA area today).
- `platform/fm1/loader/ldr_core.c` and `loader.c`: the update loader writes only
  `[0x4000, 0x93000)` and erases update records ("4K boundary - 256", magic `0x5441` at +6
  and a CRC16) in `[0x93000, 0xFC000)` **except** `[0x97000, 0xE0000)`, "Felucca's store:
  user data that may look like one". `platform/fm1/src/ota.c`: the staging area
  `[0xE0000, 0xE5000)` and its record at 0xE4F00.
- fm1-emu's flash model (`fm1-soc/src/spiflash.rs` at the pinned rev): JEDEC `85 60 14`,
  erase and page program instantaneous, a program ANDs bytes in, busy never set. The flash
  is `soc.flash.mem`, which a test can read, write and carry into a new `Machine`.
- `docs/TODO.md`: "The full boot sequence once after an install (M2 storage)".
- `app/midi_learn.h` (the bindings to persist), `app/views.h` (CARDS), `app/boot.h`.

**The flash map this plan fixes** (docs/hardware.md gets it as a table in Task 1):

| Range | Size | Owner |
|---|---|---|
| `[0x000000, 0x004000)` | 16 KiB | the device's flash head (SPL, isd_config): never written by anyone but the vendor |
| `[0x004000, 0x093000)` | 572 KiB | the app area; the update loader writes it; SIDOU's image is 0x8DFBC of it from 0x02000120 |
| `[0x093000, 0x097000)` | 16 KiB | update records' scan range (no SIDOU data) |
| `[0x097000, 0x0E0000)` | 292 KiB, 73 sectors | **SIDOU's store** (Felucca's main store on Felucca) |
| `[0x0E0000, 0x0E5000)` | 20 KiB | the update protocol's staging area and its record (0xE4F00) |
| `[0x0E5000, 0x100000)` | 108 KiB | not SIDOU's: Felucca's autosave, voice bank, globals; the stock firmware's VM; never written |

### Task 1: The flash map, the store's region and its guards

**Why first:** every later task writes flash; this one makes the boundaries code, with
tests, before any write exists.

**Files:**
- `app/store_layout.h` (new, portable): `STORE_LO 0x97000u`, `STORE_HI 0xE0000u`,
  `STORE_SECTOR 0x1000u`, `STORE_SECTORS 73u`; **the guard band**: bytes `0xF00..0xFFF` of
  every store sector are never programmed (`STORE_SECTOR_USE 0xF00u`). An update record the
  SPL or the loader could take is 80 bytes at a sector's `0xF00` with `0x5441` at +6 and a
  matching CRC16 (`ota.c`); an erased guard band reads `0xFFFF` there, so no store content
  can ever look like one, wherever the SPL scans. The loader also skips this range already.
- `platform/fm1/midi.c`: `FL_RANGE_OK` becomes the OTA area **or** the store range
  (`FL_IN(off, n, STORE_LO, STORE_HI)`), and the store's own hooks (Task 4) check the guard
  band too. The update protocol's hooks (`ota_flash.h`) keep checking the OTA area only.
- `docs/hardware.md`: a "Flash map" section with the table above, the sources, and the
  guard band's reason.
- `host/crates/sidou-tests/tests/app/store_layout.rs` (new): the layout's constants against
  the loader's (`LDR_DATA_LO/HI`, `LDR_APP_HI`, `LDR_REC_LO/HI`, read from
  `platform/fm1/loader/ldr_core.c`'s text so a change there fails here), `OTA_AREA` and
  `OTA_AREA_LEN`, the app slot (`app.ld`'s XIP length plus 0x4000 and 0x120 must end below
  0x93000), and that `[STORE_LO, STORE_HI)` is whole sectors.
- `host/crates/emu-gate/tests/flash_budget.rs` (new): `sidou_app.bin`'s size against
  `IMAGE_CEILING` (372,000 for M2a; each later plan updates it, see the overview); fails above.

**Spec notes:**
- The plain XIP window: Felucca's `fl_plain_window_init` maps flash from 0x93000 up
  unencrypted, so the store can be read straight through XIP (`fm1_xip_ptr`) instead of
  through `fl_read_ram` with XIP off. SIDOU does not call it yet. Add it to boot (before
  anything reads the store, after `update_boot`), and check in the emu that a byte written
  into `soc.flash.mem` at `STORE_LO` reads back through XIP. If the window disturbs the update
  protocol's reads (`ota_fread` uses `fl_read_ram`, so it should not), document why it does
  not.

**Tests:** the layout test above; an fm1-emu test that the plain window reads the store
plain; `flash_budget.rs`. The existing package and update tests still pass
(`cargo test --release -p sidou-pack`).

**Docs:** `docs/hardware.md` (flash map), `TESTING.md` (the new tests).

### Task 2: The store's core, portable, with power-loss tests

**Files:**
- `app/store.h`, `app/store.c` (new): portable C11, no allocation, no hardware. The flash
  is reached only through a small interface the caller supplies:
  ```c
  typedef struct {
      const uint8_t* (*map)(void* ctx, uint32_t off);           /* read: a pointer into flash */
      int (*prog)(void* ctx, uint32_t off, const void* p, uint32_t n); /* within one 256-byte page */
      int (*erase)(void* ctx, uint32_t sector_off);             /* one 4 KiB sector */
      void* ctx;
  } store_flash;
  ```
  `prog` and `erase` may be slow and may be refused for now (the device's windows, Task 4):
  the core never calls them in a loop inside one call. It is a state machine driven by
  `store_poll(store*)`, which does at most one flash operation per call and returns whether
  more work is queued. Reads are free (`map`).
- **Sector format:** a 32-byte header at offset 0: magic `"SIDOUSTR"`, format version
  (`STORE_FORMAT 1`), the sector's sequence number (u32, from a global counter, newest
  highest), its erase count, a CRC-32 of the header. Records from offset 32 up to
  `STORE_SECTOR_USE` (0xF00). The guard band stays erased.
- **Record format** (4-byte aligned): `type` (u8), `flags` (u8), `len` (u16), `key` (u32),
  `seq` (u32), `crc` (u32, of the header's first 12 bytes and the data), the data padded to
  4 bytes, then a **commit word** programmed last (`0x00000000`; erased `0xFFFFFFFF` means
  the write was cut). A record is valid only with a good CRC and a commit word of 0.
- **Keys:** small typed objects (settings, the learn map, a user profile slot) are one
  record each, latest `seq` wins, a tombstone deletes. Files are Task 3's.
- **Mount** (`store_mount`): scan every sector's header and records once (≤ 73 × 3.8 KB of
  XIP reads; spread over `store_poll` calls if one call would exceed the poll allowance on
  the device, measured in Task 4), build a RAM index (per sector: sequence, erase count,
  live bytes, free offset; per key: where its newest record is). The **head** is the newest
  sector with room. Anything after the last valid record of a sector (a cut write) makes
  that sector full: the next write goes to a fresh, erased sector. Never program over bytes
  that are not erased.
- **States of the region:** blank (all 0xFF: format lazily, writing headers as sectors are
  first used); SIDOU's (headers valid; an older `STORE_FORMAT` is migrated in RAM on read);
  **foreign** (not blank, no SIDOU headers: another firmware's data, e.g. Felucca's
  projects). Foreign is never formatted silently: `store_mount` reports it, and Task 5
  asks the user.
- **Garbage collection:** keep at least `STORE_RESERVE` (2) erased sectors. When the
  erased count falls to it, pick the victim with the least live data (oldest on a tie), copy
  its live records to the head (programs only), then queue its erase. Erases are queued,
  never done inside a write: the device runs them only when the audio is quiet (Task 4), so
  writes never wait for one unless the reserve is gone (then `store_write` returns
  `STORE_NEED_ERASE` and the caller decides: Task 4's held erase).
- **Wear:** writes go to the erased sector with the lowest erase count. NOR parts endure
  about 100k cycles a sector; a settings save a minute for ten years is about 5M record
  writes, spread over 73 sectors of ~200 records each: under 400 erases a sector. Document
  the arithmetic in the header.
- **API sketch** (refine, keep it small): `store_init`, `store_mount`, `store_state`,
  `store_get(key, buf, cap) -> len`, `store_put(key, type, data, len)`, `store_delete`,
  `store_poll`, `store_busy`, `store_stats` (free bytes, erased sectors, erase counts).

**Host tests** (`host/crates/sidou-tests/tests/app/store.rs`, new; bindings in `sidou-sys`):
- a Rust **NOR flash simulator** with the part's semantics: a program can only clear bits
  (AND), within one 256-byte page, wrapping inside the page as the part does; an erase sets
  a sector to 0xFF; reads are plain;
- **power loss at every step:** run random sequences of puts, deletes and GCs; for every
  flash operation in the sequence, cut power *during* it, with a torn outcome: a program
  that cleared any subset of its bits, an erase that left any mix of old and 0xFF bytes;
  then remount. After every cut: the store mounts; every key reads either its value from
  before the interrupted operation's transaction or after it, never a mix and never an
  older one; nothing committed before is lost; the guard bands are all 0xFF. Thousands of
  seeds (bounded time: run the long version with `-- --ignored`);
- wear: after a long random run, erase counts stay within a small spread;
- full region: writes report `STORE_FULL` cleanly, and deleting makes room after a GC;
- foreign data: a region of Felucca-like bytes mounts as foreign and nothing is written;
- format versions: a fixture image of `STORE_FORMAT 1` checked in as test data
  (`tests/data/store-v1.bin`, REUSE annotated) mounts identically in every later version
  (the migration rule of design doc section 5);
- a fuzz-style test: random bytes in the region never crash `store_mount` (ASan/UBSan).

**Gates:** none on the device yet. UBSan and ASan as the other app tests.

**Docs:** `TESTING.md` (store tests, the long run).

### Task 3: Files on the store (for songs and dumps)

**Files:** `app/store.h`/`.c` (extended), tests in `tests/app/store.rs`.

**Spec:**
- A file is a name (up to 16 characters, the font's character set, upper case), a type
  (`STORE_FILE_SONG`, room for M3's `.sid` and the starter pack), and up to
  `STORE_FILE_MAX` bytes (64 KiB; GT2 songs SIDOU can hold are well under, M2c Task 2).
- Written as **chunk records** (type CHUNK, the file's id, the chunk's index, ≤ 1,024 bytes
  of data) followed by one **FILE record** (id, name, type, length, chunk count, CRC-32 of
  the whole) that commits it. A file without its FILE record does not exist; replacing a
  file writes the new one completely, then its FILE record supersedes the old one (same
  name), then the old chunks become garbage. So a cut at any point leaves the old file or
  the new one.
- **Streaming:** `store_file_begin(name, type, length)`, `store_file_write(h, p, n)` (any
  sizes; buffered to chunk records), `store_file_end(h)`; and a reader that yields the file
  in pieces (`store_file_read(h, off, p, n)`) straight from XIP. So M2c parses a song and
  M2e streams a SysEx dump without holding the file twice in RAM.
- **Directory:** `store_dir_next` walks the committed files (name, type, length) in name
  order; `store_file_delete`; `store_file_rename`.
- **Space check before writing:** `store_file_begin` refuses (`STORE_FULL`) when the file
  cannot fit even after GC, so a song save never half-fills the store.

**Host tests:** files survive power cuts at every step (old or new, never neither, never a
mix); many files written, replaced, deleted, renamed under random cuts; a file of exactly
the maximum; a file larger than the free space is refused before anything is written;
directory order; reading at every offset and length.

### Task 4: The store on the device: write windows, quiet erases, persistence in fm1-emu

**Files:**
- `platform/fm1/store_fm1.c`, `store_fm1.h` (new): the device's `store_flash`.
  - `map`: `fm1_xip_ptr(off)` (the plain window from Task 1). After a program or erase,
    the driver already invalidates the cache lines it touched (`fl_inval` in
    `fl_prog_ram`/`fl_erase4k_ram`).
  - **`prog` in a window:** a page program masks interrupts and turns XIP off for its
    duration, during which neither the audio interrupt (its pulldown rows are read from
    flash) nor TIMER5 can run. The DMA keeps playing the queued half meanwhile. So a
    program runs only **right after an audio block**: `audio_fill` counts blocks
    (`audio_blocks()`), and `prog` waits for the count to change, then programs at most
    `STORE_WINDOW_BYTES` (start at 64; Task 4 measures) with interrupts off, and returns
    (the core calls again for the rest). The next block's interrupt fires late by the
    window's length; the gate below bounds it.
  - **`erase` only on a quiet hold:** a 4 KiB erase takes tens to hundreds of
    milliseconds, far longer than a block. `audio_hold(1)` makes `audio_fill` fade its
    output to 0 over one block and then write silence; once both DMA halves hold silence,
    the erase runs with interrupts masked (the DMA loops a silent half), then
    `audio_hold(0)`. Chips and the song clock do not advance meanwhile. The store's
    queued erases run only when the audio is **quiet**: no gate open on any voice (the
    instrument's and, from M2c, the player's), the output's block peak below about
    -60 dBFS for 500 ms (a per-block peak in `audio_fill`, ≤ 2 instructions a sample,
    counted against the audio budget), no MIDI byte for 500 ms, no SysEx transfer
    running. Also at boot, before the audio starts, at most one queued erase.
  - **`STORE_NEED_ERASE` during play:** if a save finds the reserve gone (rare: GC keeps
    two erased sectors), the save waits for quiet; an explicit SAVE that has waited 2 s
    runs the held erase anyway (a short gap the user asked for) and says so in the toast.
- `platform/fm1/main.c`: `store_mount` at boot (before `ui_init`, after `update_boot`),
  `store_poll` once per main-loop pass, after `midi_service`, only when the pass has room.
- `platform/fm1/audio.c`: the block counter, the peak, `audio_hold`.
- `platform/fm1/app.ld`: nothing new in `.ram_text` unless the window code needs it (the
  `fl_*_ram` functions are there already). Note the RAMTEXT figure in the commit.

**Tests** (`host/crates/emu-gate/tests/store.rs`, new):
- **persists:** boot, put a value (a test hook: a CC the firmware maps to a store write
  only in test builds, or the settings of Task 5 once it exists), let the store write, read
  `soc.flash.mem`, boot a fresh `Machine` with that flash, the value is there;
- **power cut in the emulator:** stop the machine after the k-th flash program command
  (count the changes `soc.flash.changed` reports) for every k of a settings save and of a
  GC, boot a fresh machine with the flash as it was, and assert the store mounts with the
  old or the new value;
- **the window's cost:** the longest interrupts-off stretch during a save, in
  instructions (the emulator counts them; the flash itself is instantaneous there), and
  that no audio block is missed: every ALNK0 half filled before the DMA reached it; at
  most 1 ms at 240 MHz including a budgeted program time for the real part (estimate from
  the datasheet, flagged for hardware);
- **no erase while it plays:** with a held chord, queue a GC: no erase happens until the
  keys are released and the peak falls; then it runs, the hold fades out and back;
- **the poll allowance:** every main-loop pass during mount, saves and GC within
  `POLL_INSTRUCTIONS`; the latency gate (`latency.rs`) passes with a save running;
- the ALNK0 interrupt still runs only `.ram_text` (`ram_audio.rs`).

**Hardware flags:** the part's page program and erase times (`took_us`), and whether a
masked millisecond ever drops a block on the device; add both to `docs/hardware-test.md`
(a save while a chord plays, listened to) and `docs/hardware.md`'s open checks.

**Docs:** `docs/hardware.md` (how the store writes: windows and quiet erases),
`TESTING.md`.

### Task 5: Settings that persist, the full boot once, and SAVE

**Files:** `app/settings.h`, `app/settings.c` (new, portable): the settings record, its
schema and migrations; `app/views.c`, `app/boot.c`, `app/learn_view.c`, `app/midi_learn.c`,
`platform/fm1/ui.c`, `platform/fm1/main.c`.

**What persists** (the record `settings` v1, one store key, versioned; later plans add
fields through a migration and a fixture each):
- CARDS (title cards on or off);
- MIDI learn's bindings (`midi_learn`'s table);
- the envelope mode (INSTANT or AUTHENTIC);
- each chip's profile, character controls and the effect slots' settings (the instrument
  as it was left), and the preset;
- the firmware version last booted (the "full boot once" flag, below);
- reserved for M2b (KEYS chip, UI sounds), M2c (the last song), M2e (MIDI mode and
  channels).

Not persisted: octave, held notes, the controllers, the view on screen.

**Behaviour:**
- **Load at boot:** after `store_mount`, before `live_init` sends its registers, so the
  instrument starts as it was left; a missing or unreadable record means M1's defaults.
- **Save:** debounced: 5 s after the last change to a persisted value, as a background
  write (page programs only; it never needs an erase unless the reserve is gone). No toast
  for background saves.
- **The full boot once after an install** (`docs/TODO.md`): at boot, if the stored version
  differs from the firmware's (or is missing), play the full boot sequence and store the
  version; otherwise the short one. HOME held at power-on still plays the full one. Remove
  the TODO entry.
- **Foreign data:** if `store_mount` reports another firmware's data, nothing persists and
  the menu shows STORE: FOREIGN; turning ALGORITHM clockwise twice on it (a confirm) formats
  the store (all 73 sectors erased with the audio held, a progress line on the screen, a few
  seconds). Never automatic.
- **SAVE** (to confirm with the user, overview "Risks"): a **press and release** of SAVE
  without a knob turned saves now (settings, and from M2c the song), with a toast `SAVED`
  (and M2b's drive "chunk" if UI sounds are on); **SAVE held while a knob turns** arms MIDI
  learn exactly as M1d's hold form does; learn's clear (SAVE three times) and forget (SAVE
  instead of a CC while armed) gestures stay. Update `docs/reference/controls.md`, "MIDI
  learn" and the reasoning paragraph about SAVE, and `docs/reference/midi.md` through its
  generator (`SIDOU_MIDI_DOC_UPDATE=1`).
- **Menu:** a STORE item (after CARDS) showing the free space (`STORE 212K FREE`) or
  FOREIGN, and the format confirm.

**Tests:**
- host (`tests/app/settings.rs`): the record round trips; every field's default; a v1
  fixture (`tests/data/settings-v1.bin`) loads in every later schema; migrations fill new
  fields with their defaults; the debounce (a burst of changes, one write);
- fm1-emu: change CARDS, the envelope mode and a learn binding; let the debounce pass;
  reboot with the flash; all three are back; the boot is short; a flash with an older
  stored version plays the full boot once, then short; a foreign region shows FOREIGN and
  the confirm formats it; SAVE's press saves, SAVE held with a knob arms learn (M1d's learn
  tests updated and still passing);
- the LCD goldens for the menu with STORE.

**Docs:** `docs/reference/controls.md` (SAVE, STORE), `docs/art/README.md` ("Boot": the

## Risks and open questions

- **Program and erase times on the real part** are unknown (fm1-emu makes them
  instantaneous). If a 64-byte program does not fit beside a block, the window shrinks to
  16 bytes (more windows, same safety); if even that drops blocks, settings saves wait for
  quiet too. Hardware check.
- **Erase-suspend** would let erases run during play; not relied on (the part's support and
  the driver are unverified). A possible later improvement.
- **The SPL's record scan range** is not documented; the guard band makes store sectors
  unable to look like a record wherever it scans.
- **Foreign data** from Felucca or another firmware: formatting loses it; the confirm and
  the installer's "back up user songs before flashing" (design section 10) are the
  protection. The installer's backup is M4's; M2e adds a SysEx store backup.
- **Going back to stock V15** may or may not use this range; SIDOU's CRCs catch damage, and a
  damaged store mounts as foreign or with the damaged records dropped.
