# M2a: Storage, implementation plan

<!-- REUSE-IgnoreStart -->

> **For Claude:** REQUIRED SUB-SKILL: use superpowers:subagent-driven-development
> to implement this plan task by task.

**Goal:** SIDOU keeps what the player sets, across power cycles and firmware updates:
settings, MIDI learn's map, the CARDS option, the "full boot once after an install" flag,
user chip profiles, and (for M2c) song files. In a log-structured store in the free flash
region, safe against power loss at any instant, without audible glitches during play, and
never in the way of the update protocol.

**Overview and budgets:** [2026-10-15-m2-overview.md](2026-10-15-m2-overview.md). This plan
needs nothing from the other M2 plans, except Task 6's expert fields (M2b Task 6, added by
that task through a migration). M2c Task 8, M2d and M2e build on it.

**The flash map this plan fixes** (docs/hardware.md gets it as a table in Task 1):

| Range | Size | Owner |
|---|---|---|
| `[0x000000, 0x004000)` | 16 KiB | the device's flash head (SPL, isd_config): never written by anyone but the vendor |
| `[0x004000, 0x093000)` | 572 KiB | the app area; the update loader writes it; SIDOU's image is 0x8DFBC of it from 0x02000120. **Fixed:** the store's size is not a lever for the image |
| `[0x093000, 0x097000)` | 16 KiB | the first 16 KiB of the package's VM region; inside the loader's record scan (it erases update records it finds there); the stock firmware's VM data may live here. Neither SIDOU nor Felucca writes it |
| `[0x097000, 0x0E0000)` | 292 KiB, 73 sectors | **SIDOU's store** (Felucca's main store on Felucca); inside the VM region; the loader's scan skips it |
| `[0x0E0000, 0x0E5000)` | 20 KiB | the update protocol's staging area and its record (0xE4F00); inside the VM region |
| `[0x0E5000, 0x0E9000)` | 16 KiB | the end of the VM region: Felucca's autosave and voice bank, the stock OTA's VM backup (0xE8000); never written by SIDOU |
| `[0x0E9000, 0x100000)` | 92 KiB | not SIDOU's: Felucca's globals (0xFC000) and the rest; never written |

**Why nothing acts on the VM descriptor:** the region is the SDK's VM store, which only
SDK code reads or formats (the stock app's syscfg). SIDOU links no SDK VM code and runs
none; the update loader is SIDOU's own (`ldr_core.c`) and ignores the descriptor; Felucca
ships the same descriptor and has stored user data in `[0x97000, 0xE0000)` on these units
since its 1.x releases. What the stock SPL does with the descriptor is not known: a
hardware check (Task 3b, and the overview's hardware flags).

### Task 1: The flash map, the store's region and its guards

**Why first:** every later task writes flash; this one makes the boundaries code, with
tests, before any write exists.

**Files:**
- `app/store_layout.h` (new, portable): `STORE_LO 0x97000u`, `STORE_HI 0xE0000u`,
  `STORE_SECTOR 0x1000u`, `STORE_SECTORS 73u`; **the guard band**: bytes `0xF00..0xFFF` of
  every store sector are never programmed (`STORE_SECTOR_USE 0xF00u`). An update record the

### Task 2: The store's core, portable, with power-loss tests

**Files:**
- `app/store.h`, `app/store.c` (new): portable C11, no allocation, no hardware. The flash
  is reached only through a small interface the caller supplies:
  ```c
  typedef struct {
      const uint8_t* (*map)(void* ctx, uint32_t off);                  /* read: a pointer into flash */
      int (*prog)(void* ctx, uint32_t off, const void* p, uint32_t n); /* within one 256-byte page */
      int (*erase)(void* ctx, uint32_t sector_off);                    /* one 4 KiB sector */
      void* ctx;
  } store_flash;
  ```
  `prog` and `erase` return `STORE_OK`, an error, or **`STORE_LATER`** (not now: the device
  has no window open, Task 4). The core never waits and never retries inside a call: it is
  a state machine driven by `store_poll(store*)`, which does at most one flash operation
  per call, and on `STORE_LATER` keeps the operation for the next call. Reads are free
  (`map`).
- `docs/reference/store-format.md` (new): the on-flash format below, byte for byte, and a
  **"Magic numbers"** table: `"SIDOUSTR"` (a store sector's header, this file) and
  `"SIDOU-X\0"` (a song file's trailer, `docs/reference/song-format.md`, M2c Task 1), so
  a reader of a flash dump or a file finds both in one place.

**Sector format** (32-byte header at offset 0, written in two steps):
- **Erase header**, programmed right after the sector's erase completes: bytes 0-7 magic
  `"SIDOUSTR"`, 8-9 format version (`STORE_FORMAT 1`), 10-11 zero, 12-15 the sector's
  erase count, 16-19 a CRC-32 of bytes 0-15. A sector whose erase header is valid and whose
  bytes 20..0xEFF all read 0xFF is **clean** and may be used.
- **Claim**, programmed when the sector is taken into use: bytes 20-23 the sector's
  sequence number (from a global counter, newest highest), 24-27 a CRC-32 of bytes 0-23,
  28-31 the claim word `0x00000000`.
- **A sector without a valid erase header is dirty, whatever it reads** (a cut erase can
  leave bytes that read 0xFF and do not hold a program): mount never treats it as erased;
  it is queued for an erase before any use. A clean sector with a cut claim (a bad claim
  CRC or a claim word not 0) is dirty too.
- Records from offset 32 up to `STORE_SECTOR_USE` (0xF00): **0xEE0 (3,808) bytes a
  sector**. The guard band stays erased.

**Record format** (4-byte aligned): a 16-byte header: `type` (u8), `flags` (u8), `len`
(u16), `key` (u32), `seq` (u32), `crc` (u32, of the header's first 12 bytes and the data);
the data padded to 4 bytes; then a **commit word** (`0x00000000`; erased `0xFFFFFFFF`
means the write was cut). Order of programming: the data first, then the header, then the
commit word (all three land on erased bytes, so the order is free; data first lets a long
record stream its data without holding it in RAM, Task 3). A record is valid only with a
good CRC and a commit word of 0.

**Keys and versions:**
- Small typed objects (settings, the learn map, a user profile slot) are one record each;
  the newest `seq` wins; a tombstone deletes. Files are Task 3's.
- **Every write takes the next `seq`, a GC copy too** (as built; the first design kept a
  copy's `seq`, and a copy cut in its commit word then was not the newest record, so
  nothing repaired it: a deleted key could come back, the third review's C1). One write is
  in flight at a time, so the write a cut interrupted is always the newest record. Two valid
  records of a key with equal `seq` arise only in regions written before that rule (a record
  and its copy, the same bytes: the one in the sector with the higher claim number wins);
  with different data, mount counts it as corruption in `store_stats`.
- **Recovery** (as built, `docs/reference/store-format.md`, "Faint bits and the head"):
  the newest record counts when its CRC checks and is copied forward before the session
  writes; ambiguous sectors (a cut tail, a sector read as killed, a torn erase or claim) are
  evacuated and erased before the session writes. Writes answer `STORE_BUSY` until then;
  the boot's pool fill absorbs it.

**Mount** (`store_mount`): scan every sector's header and records once (≤ 73 × 3.8 KB of
XIP reads, in slices of at most `STORE_POLL_WORST` instructions across `store_poll` calls),
build a RAM index (per sector: state, sequence, erase count, live bytes, free offset; per
key: where its newest record is). The **head** is the newest claimed sector with room.
Anything after the last valid record of a sector (a cut write: an erased header with
programmed bytes after it, a bad CRC, a missing commit word) makes that sector full: the
next write goes to a fresh, clean sector. Never program over bytes that are not erased.

**States of the region:** blank (all 0xFF and no headers: every sector is dirty; the
store formats lazily, erasing and writing erase headers as the pool fills); SIDOU's
(headers valid; an older `STORE_FORMAT` is migrated in RAM on read); **foreign** (not
blank, no SIDOU headers: another firmware's data, e.g. Felucca's projects). Foreign is
never formatted silently: `store_mount` reports it, and Task 5 asks the user.

**The erase-ahead pool:**
- Clean, unclaimed sectors form the pool. **`STORE_POOL_MIN` = `ceil(STORE_FILE_MAX /
  0xEE0) + 2`** = ceil(65,536 / 3,808) + 2 = **20** sectors: enough for the largest file
  (Task 3) plus GC's two-sector reserve. A `_Static_assert` checks it against Task 3's real
  packing (three chunk records a sector, 3,744 data bytes: ceil(65,536 / 3,744) = 18, plus
  2 = 20); if the packing ever needs more, the larger number is the minimum.
- The pool is **refilled toward `STORE_POOL_TARGET` (22)** whenever the device is quiet
  (Task 4): GC copies a victim's live records and erases it; dirty sectors are erased. Two
  sectors above the minimum let a few settings writes claim a new head sector without
  taking the pool below what the largest file needs.
- Whoever needs sectors **claims them from the pool before writing a byte**: a new head
  sector for small records; all of a file's sectors at `store_file_begin` (Task 3). GC's
  own reserve (the last 2) is claimed only by GC.
- So during play no write ever waits for an erase: every program lands in a sector the
  pool already holds. When the pool cannot cover a request, the request is refused with
  **`STORE_BUSY`** (the pool refills when quiet) or `STORE_FULL` (it cannot fit even after
  GC), never half-done.

**Garbage collection:**
- Pick the victim with the least live data (the oldest sector sequence on a tie), copy its
  live records into the head (programs only, each copy a new `seq`), and only when every
  copy is committed, kill the victim, mark it dirty in RAM and erase it before any other
  maintenance.
- **Tombstones are carried forward** while any older record of their key survives in
  another sector (not the victim); a tombstone whose key has no older record anywhere else
  is dropped. Otherwise a deletion could come undone when the tombstone's sector is
  collected before the older record's.
- Erases are queued, never done inside a write; the device runs them only when quiet
  (Task 4).

**Wear:** a sector is taken from the pool by the lowest erase count. NOR parts endure about
100k cycles a sector; a settings save a minute for ten years is about 5M record writes,
spread over the 53 sectors outside the pool's minimum at ~200 records each: under 500
erases a sector. Document the arithmetic in the header. (The pool's 20 sectors rotate with
the rest; they are not fixed sectors.)

**API sketch** (refine, keep it small): `store_init`, `store_mount`, `store_state`,
`store_get(key, buf, cap) -> len`, `store_put(key, type, data, len)`, `store_delete`,
`store_poll`, `store_busy`, `store_erase_wanted` (an erase is queued: Task 4's quiet
detector looks at it), `store_stats` (free bytes outside the pool, pool size, dirty
sectors, erase counts, corruption seen).

**Host tests** (`host/crates/sidou-tests/tests/app/store.rs`, new; bindings in `sidou-sys`):
- a Rust **NOR flash simulator** with the part's semantics: a program can only clear bits
  (AND), within one 256-byte page, wrapping inside the page as the part does; an erase sets
  a sector to 0xFF; reads are plain; and a `STORE_LATER` mode that refuses a random share of
  programs and erases, to prove the core retries;
- **power loss at every step:** run random sequences of puts, deletes and GCs; for every
  flash operation in the sequence, cut power *during* it, with a torn outcome: a program
  that cleared any subset of its bits, an erase that left any mix of old and 0xFF bytes
  (including **all 0xFF with no erase header**); then remount. After every cut: the store
  mounts; every key reads either its value from before the interrupted operation's
  transaction or after it, never a mix and never an older one; nothing committed before is
  lost; a deleted key stays deleted (the tombstone rule, with GC orders that collect the
  tombstone's sector first); the guard bands are all 0xFF; a sector cut mid-erase is
  re-erased before it is used. Thousands of seeds (bounded time: run the long version with
  `-- --ignored`);
- the pool: after any operation the pool is ≥ `STORE_POOL_MIN` or the operation was
  refused with `STORE_BUSY`; a refill with quiet brings it back to the target;
- wear: after a long random run, erase counts stay within a small spread (max minus min
  ≤ 8 after 10,000 erases);
- full region: writes report `STORE_FULL` cleanly, and deleting makes room after a GC;
- foreign data: a region of Felucca-like bytes mounts as foreign and nothing is written;
- format versions: a fixture image of `STORE_FORMAT 1` checked in as test data
  (`tests/data/store-v1.bin`, REUSE annotated) mounts identically in every later version
  (the migration rule of design doc section 5);
- a fuzz-style test: random bytes in the region never crash `store_mount` (ASan/UBSan).

**Gates:** none on the device yet. UBSan and ASan as the other app tests.

**Docs:** `docs/reference/store-format.md` (new), `TESTING.md` (store tests, the long run).

### Task 3: Files on the store (for songs and dumps)

**Files:** `app/store.h`/`.c` (extended), tests in `tests/app/store.rs`,
`docs/reference/store-format.md` (the file records).

**Spec:**
- A file is a name (up to 16 characters, the font's character set, upper case), a type
  (`STORE_FILE_SONG`, room for M3's `.sid` and the starter pack), and up to
  **`STORE_FILE_MAX` = 65,536 bytes** (M2c's largest `.sng` with its trailer fits: M2c
  Task 2 caps a song's GT2 part and trailer to the content region's arena and extension).
- Written as **chunk records** (type CHUNK, the file's id, the chunk's index, **1,248 bytes
  of data**, the last chunk shorter) followed by one **FILE record** (id, name, type,
  length, chunk count, CRC-32 of the whole) that commits it. A chunk record takes
  16 + 1,248 + 4 = 1,268 bytes, so **three fill a sector's 3,808 bytes** (3,804) and a
  sector carries 3,744 bytes of a file; a 64 KiB file takes 18 sectors. A file's chunks go
  only into the sectors claimed for it; its FILE record goes into the head.
- A file without its FILE record does not exist; replacing a file writes the new one
  completely, then its FILE record supersedes the old one (same name), then the old chunks
  become garbage. So a cut at any point leaves the old file or the new one.
- **Claimed before the first byte:** `store_file_begin(name, type, length)` claims
  `ceil(length / 3,744)` sectors from the pool and a place for the FILE record in the head,
  **all before it returns**, so a caller (a save, a SysEx `PUT` before its first `ACK`,
  M2e Task 5) knows the whole file will land without an erase. It returns `STORE_BUSY` if
  the pool, less GC's reserve, cannot cover it now, and `STORE_FULL` if the file cannot fit
  even after GC; nothing is written in either case. A file ended short (fewer bytes than
  `length`) or aborted returns its unused claimed sectors to GC (they hold no valid FILE
  record, so they are garbage).
- **Streaming without a chunk buffer:** `store_file_write(h, p, n)` copies into a
  `STORE_WINDOW_MAX`-byte staging buffer (256 bytes) and returns how many bytes it took
  (back-pressure: the caller offers the rest on a later pass); `store_poll` programs a
  chunk's data from it a window at a time, accumulating the chunk's CRC, then the chunk's
  header, then its commit word (Task 2's order). `store_file_end(h)` writes the FILE
  record. RAM: the staging buffer and a handle, under 300 bytes.
- A reader that yields the file in pieces (`store_file_read(h, off, p, n)`) straight from
  XIP, so M2c parses a song and M2e streams a SysEx dump without holding the file twice in
  RAM.
- **Directory:** `store_dir_next` walks the committed files (name, type, length) in name
  order; `store_file_delete`; `store_file_rename`.

**Host tests:** files survive power cuts at every step (old or new, never neither, never a
mix); many files written, replaced, deleted, renamed under random cuts; a file of exactly
`STORE_FILE_MAX`; a file larger than the free space is refused before anything is written;
`store_file_begin` with the pool short returns `STORE_BUSY` and writes nothing, and the
same begin succeeds after a refill; the claimed sectors equal ceil(length / 3,744); no
erase is ever issued between `store_file_begin` and `store_file_end` (the simulator
counts); directory order; reading at every offset and length; `store_file_write`'s
back-pressure with offers of every size from 1 to 1,000 bytes.

**Decision rule** (Task 4 applies it to the recorded numbers; write it into
`docs/hardware.md` now):
- **Programs in windows** if the worst 16-byte program plus the driver's overhead is
  ≤ 1,000 µs: `STORE_WINDOW_BYTES` is the largest of 16, 64 and 256 whose worst time fits.
  Otherwise programs become **held operations** like erases (quiet only), and settings
  saves wait for quiet.
- **Erases:** a held 4 KiB sector erase if its worst time is ≤ 30 ms; else 16 held page
  erases (0x81) a sector if the part has them and each is ≤ 30 ms; else erase-suspend in
  ≤ 30 ms slices if it works; else erases only at boot (before the audio starts, at most
  `STORE_POOL_TARGET` sectors) and on an explicit format, and the pool is sized at boot
  for the session. 30 ms leaves 5 ms under the 35 ms hold budget for the driver.
- At 360 MHz every instruction-count margin in M2 grows by half; at 240 MHz they are as
  written. The spike records which.
- **Partial programs:** if the part limits partial programs per page below
  `STORE_PAGE_PROGS` (34), or has ECC, the store's format changes before Task 4 (records in
  single-shot 16-byte units). If programming 0 over 0 is outside its spec, the claim programs
  bytes 20-31 only (no longer the erase header again), and every clean sector a mount finds
  is erased again before its first claim, at most `STORE_POOL_TARGET` erases a boot. That is
  the whole change: the newest record is copied forward already, and the kill never programs
  a bit that reads 0 (`docs/reference/store-format.md`, "Partial programs and ECC"). The one
  zeros-over-zeros program left after that is a kill after a kill cut short, over the bits
  that cut left faint and reading 1; recorded, not avoided.

### Task 4: The store on the device: write windows, quiet erases, persistence in fm1-emu

**Needs:** Task 3b's numbers in `docs/hardware.md`. If they are not there, stop and report.

**Files:**
- `platform/fm1/store_fm1.c`, `store_fm1.h` (new): the device's `store_flash`.
  - `map`: `fm1_xip_ptr(off)` (the plain window from Task 1). After a program or erase,
    the driver already invalidates the cache lines it touched (`fl_inval` in
    `fl_prog_ram`/`fl_erase4k_ram`).
  - **`prog` in a window, never waiting:** a page program masks interrupts and turns XIP
    off for its duration, during which neither the audio interrupt (its pulldown rows are
    read from flash) nor TIMER5 can run; the DMA keeps playing the queued half meanwhile.
    The audio interrupt **stamps the end of each block** (`audio_block_end`, a 24 MHz tick
    count written as its last act). `prog` masks interrupts, reads the time, and proceeds
    only if **now − stamp ≤ `STORE_WINDOW_LEAD_US` (250 µs)** and the next half's interrupt
    is not pending; otherwise it unmasks and returns `STORE_LATER` at once, and the core
    keeps the operation for a later `store_poll` pass. It programs at most
    `STORE_WINDOW_BYTES` (Task 3b's decision) and returns. A commit word is always one 4-byte
    program (`store_init`): with a window under 4 bytes, the window's timing must cover 4.
  - **`erase` holds, never waiting:** called outside a held window (the hold below not yet in
    place: audio not yet silent, quiet not established), it returns `STORE_LATER` at once and
    the core asks again on a later pass; the hook itself enforces the held window, so no
    caller can start an erase while the audio plays.
    With erase-suspend (Task 3b's third erase mode), the hook may also answer `STORE_LATER`
    for an erase it started and suspended, and finish it on a later call: the core never
    reads, programs or collects a sector it is erasing, and the host simulator's suspend mode
    (the sector reads torn until the erase resumes) checks it.
  - **Why 250 µs:** a block is 128 samples at 44,117.6 Hz, **2,901 µs**; the interrupt's
    worst fill is 2,700 × 128 = 345,600 instructions, **1,440 µs** at 240 MHz (about one
    instruction a cycle, as the budgets assume); so the next block's interrupt comes at
    least 1,461 µs after a stamp. A window that starts within 250 µs and lasts at most
    1,000 µs ends by 1,250 µs: 211 µs before the next interrupt at the worst, so a window
    never even delays a block. At 360 MHz the margin grows. `_Static_assert` the arithmetic
    from the constants.
  - **Held operations, only when quiet:** `audio_hold(1)` makes `audio_fill` fade its output
    to 0 over one block and then write silence; once both DMA halves hold silence, the
    operation runs with interrupts masked (the DMA loops a silent half), then
    `audio_hold(0)`. Chips and the song clock do not advance meanwhile. **Each held
    operation masks interrupts at most 35 ms** (Task 3b's erase mode: a sector erase, a page
    erase, or a suspend slice ≤ 30 ms plus the driver), so the TRS ring (40.96 ms) never
    overflows; consecutive held operations are at least 10 ms apart, so TIMER5 drains the
    ring between them.
  - **Quiet**, when every one of these holds: the transport is stopped (a running song is
    never quiet; with it stopped, the song's voices' gate bits left in chip A's registers
    are ignored, from M2c on); no gate open on the instrument's voices or a UI sound's;
    the output's block peak below about -60 dBFS for 500 ms; no MIDI byte for 500 ms
    **other than real-time bytes** (`F8` clock, `FE` active sensing, and `FA`-`FC` are
    ignored: a DAW sends clock and sensing all the time); no SysEx transfer running (M2e).
    The **peak scan** in `audio_fill` (≤ 2 instructions a sample, counted against the audio
    budget) **runs only while `store_erase_wanted()` and the transport is stopped** (quiet
    needs both); otherwise it costs nothing, so it never adds to a song's or (M3) a `.sid`'s
    worst block.
  - What quiet does: the pool refill (GC copies in windows, then held erases of victims and
    dirty sectors) up to `STORE_POOL_TARGET`, one held operation per 10 ms at most, and
    stops at once when quiet ends (a key, a MIDI byte, PLAY): an erase in flight finishes
    (≤ 35 ms), nothing new starts. Also at boot, before the audio starts, the pool fills to
    its target without holds.
  - **`STORE_BUSY` on an explicit SAVE** (the pool short, rare: it is sized for the largest
    file): the save waits for quiet; after 2 s it runs the held erases it needs anyway, each
    ≤ 35 ms and 100 ms apart (short gaps the user asked for), and its toast says
    `SAVED (GAPS)`. Background saves never do this: they wait for quiet.
- `platform/fm1/main.c`: `store_mount` at boot (before `ui_init`, after `update_boot`; its
  slices before the audio starts may run whole), then the pool filled to its target (each
  boot's first small write starts a fresh head, Task 2, so it needs the pool over its
  minimum; and the mount's recovery, a record's copy and after a cut an evacuation and up to
  two erases, runs first: writes answer `STORE_BUSY` until it is done); `store_poll` once per main-loop pass, after `midi_service`, its work bounded by
  `STORE_POLL_WORST`; `store_file_idle` once per pass with the milliseconds since the last
  (an open file whose sender went quiet is aborted after 5 s). `STORE_POLL_WORST` is measured
  in instructions against the host proxy `store.work` (`STORE_POLL_WORK` = 7,168 units, each
  meant as about 4 instructions or fewer: a byte scanned 1, a CRC byte 3, a key compared 1, a
  map call 3, a sector visited 2). The cost of a unit differs by kind, so Task 4 measures
  every kind of pass on the emulator, each against its own work: a mount slice of erased
  bytes, one of records, the mount's finish, a collection's scan, its plan (`due`), a
  tombstone's walk, `forget`, a copy, a file's chunk, an erase's kill; the gate holds when
  every kind's instructions per unit times `STORE_POLL_WORK` is within `STORE_POLL_WORST`. A
  kind over 4 a unit raises its weight in `store.c`, never the bound. `store_put` and `store_file_begin` CRC their data in the caller's
  pass (up to 1,264 bytes), outside `store_poll`: count them in that pass's allowance. **It skips a pass that ran
  a chip preparation slice** (M2b Task 1's slices, ≤ 40,000, run in `live_tick` once every
  10 ms; M2b Task 1 sets the flag, and until it lands no pass has one), so a pass never
  holds a frame, a slice and the store's work together (68,000 + 40,000 + 30,000 would
  exceed 120,000).
- `platform/fm1/audio.c`: the end-of-block stamp, the gated peak, `audio_hold`.
- `platform/fm1/app.ld`: `prog`'s window code and the hold's erase step in `.ram_text`
  (they run with XIP off); the `fl_*_ram` functions are there already. Note the RAMTEXT
  figure in the commit.

  guard band makes store sectors unable to look like a record wherever it scans, and Task
  3b's stock round trip checks the region survives.
- **Foreign data** from Felucca or another firmware: formatting loses it; the confirm and
  the installer's "back up user songs before flashing" (design section 10) are the
  protection. The installer's backup is M4's; M2e adds a SysEx store backup.
- **Going back to stock V15** may or may not use this range; SIDOU's CRCs catch damage, and a
  damaged store mounts as foreign or with the damaged records dropped.
