**Status:** plan, written 2026-10-18 from `main` at 3b6d28d (M2 not closed). M3 starts after

**Goal:** design doc section 14's M3, leaner, as [decision record 0008](../decisions/0008-m3-6502-and-fm1-sid.md)
sets it: PSID `.sid` tunes play on the FM-1 through SIDOU's own 6502, a frame ahead in the
main loop, with each SID write stamped with its 6502 cycle and applied at that cycle by the
audio interrupt. A browser lists the tunes on the store, a NOW PLAYING page shows the tune
with mute and solo per voice and the transport, and a starter pack of openly licensed tunes
goes on the store (never in the image). Tunes reach the device through M2e's SysEx `PUT`.
Every behaviour is checked against the PSID file spec and the real C64 (reSIDfp for the
SID's reads), and the whole write stream against a host oracle built from m6502.h and FM-1
SID's `psid.c`, tune by tune, with an explicit list of expected differences.

**Out of M3** (each stays where the design doc or the roadmap has it): RSID (recommended
below: rejected politely in M3, a later plan), RIP, SID-Wizard import and playlists of the
user's HVSC copy (M5 and the companion), the companion's own `PUT` with acknowledgements
(FM-1 Live Link), `.sid` in the browser demo (M4).

## The design, in one place

Every task below follows these decisions; none is left to an implementer.

### The 6502 (Task 1)
`core/cpu6502/` from the study's prototype: instruction-stepped, exact NMOS cycle counts
(page crossings, taken branches), all 256 opcodes (the undocumented ones as Tom Harte's
tests define them, the unstable stores' `& (high + 1)` and ANE/LXA's magic constant
`0xEE`), NMOS decimal mode, JAM stops the CPU. The 64 KiB memory is the caller's. Reads and
writes of `$D000-$DFFF` go to two hooks while `$01` maps I/O in; each hook gets the
access's cycle: a load's or store's last cycle, and a read-modify-write's two writes (the
old value, then the new) on its last two. The study's prototype matched m6502.h + `psid.c`'s
(call, cycle, register, value) stream hash exactly on all 16 tunes, so this stamp convention
is the oracle's. **The device build is `CPU6502_SMALL` (the I/O page's accesses out of line)
at `-Os`:** 9,928 bytes of code and a 256-byte cycle table in the study, against 12,812 at
`-O2` with the accesses inline; it costs about 7 % more instructions (10.1 a 6502 cycle
against 8.9), which the main loop has to spare and the flash has not.

`cpu6502_run(c, limit)` runs whole instructions until the cycle counter reaches `limit`,
the routine returns to the sentinel or a KERNAL interrupt exit, or a JAM, and can be called
again to continue: that is what slices it. The counter is the tune's 32-bit running cycle
count, compared with wrapping arithmetic (`(int32_t)(a - b)`), so it never needs resetting.

### The PSID environment (Tasks 4, 6a, 6b)
- **The header** is parsed into a `psid_header` with every field checked against the file's
  length before it is used (Task 4's table). RSID, MUS data (flag bit 0) and C64 BASIC are
  refused with their own codes; a PSID with the PlaySID-samples flag (bit 1) plays with a
  warning that its `$D41D` samples are silent.
- **Calls:** init with A = song - 1, X = Y = 0, I set, D clear, S = `$FF` after a pushed
  return address of `$0000` (an RTS lands on `$0001`); play the same with A = 0; play
  address 0 calls the tune's own interrupt handler (`$0314` when `$01` maps the KERNAL in,
  else `$FFFE`) with P pushed as an interrupt does. A call ends at a return to `$0000` or
  `$0001`, or a jump to the KERNAL's interrupt exits `$EA31`, `$EA81`, `$FEBC` (no ROM is
  emulated; those addresses stand for them). FM-1 SID's sentinel scheme, kept.
- **The bank register** is set before every init and play call from the call's address, as
  libsidplayfp's PSID driver does: `$37` below `$A000`, `$36` up to `$CFFF`, `$34` for
  `$D000-$DFFF`, `$35` from `$E000` (FM-1 SID sets `$37` once at load). The controller
  checks this rule against `SID_file_format.txt` before Task 6a starts; if the spec says
  otherwise, the spec wins and this line is corrected.
- **Limits:** init may run 5 s of 6502 time (the tune's clock × 5); past that the tune
  stops with `INIT TOO LONG`. A play call that runs past its period is an **overrun**
  (counted, shown); the next call then starts when it returns, as a C64's next interrupt
  waits for the handler's RTI. A play call that has not returned after one second of 6502
  time stops the tune with `PLAY HUNG`. A JAM stops it with `6502 JAM AT $xxxx`.
- **Time:** cycle 0 is init's first cycle. The first play call is at the first period
  boundary after init returns (`(init_end / P + 1) * P`, as `psidlog.c` schedules it); call
  n + 1 is due one period after call n was due, or at call n's return if that is later.
- **The period:** a VBI song's is the frame, PAL 19,656 cycles (312 lines of 63) or NTSC
  17,095 (263 lines of 65); a CIA song's is CIA 1 timer A's latch + 1, as the latch stands
  when the previous call returned, with no floor (FM-1 SID replaces periods under 1,000
  with the frame; SIDOU honours them). The latch starts at the KERNAL's value for the
  clock: `$4025` PAL, `$4295` NTSC. The speed bit for song n is bit `min(n, 32) - 1`, so
  songs above 32 take bit 31, as the spec says (FM-1 SID wraps to bit 0).
- **The clock:** the header's clock flags (v2+, bits 2-3): NTSC plays at 1,022,727 Hz with
  NTSC frames; PAL, "unknown" and "both" at 985,248 Hz. Chip A (and B for a 2SID tune) is
  prepared at that clock.
- **The chip model:** with the SID MODEL setting at AUTO (the default), "6581" plays the
  6581 R4AR profile (reSIDfp's defaults), "8580" the 8580 R5, and "unknown" or "both" the
  keys' setup (the user's chip choice, as decision record 0008 asks); the second SID's
  model bits (v3+, 6-7; 0 means "as the first"). With SID MODEL at KEYS every tune plays
  the keys' setup. The character controls start at zero for AUTO's two named profiles.
  While a tune plays, CHIP's A tab changes chip A as it does during a song.
- **The I/O page** (while `$01` maps it in):
  - SID: `$D400-$D7FF` is chip A (every 32 bytes a mirror), except a 2SID tune's second
    SID's 32-byte window (v3+ `secondSIDAddress`, valid `$42-$7F` and `$E0-$FE`, even
    values only, as `$Dxx0`), which is chip B and takes priority; a third SID's writes (v4)
    are dropped and counted, and the tune shows `3SID: 3RD SILENT`.
  - VIC: `$D012` and bit 7 of `$D011` give the raster line from the absolute cycle,
    `(t % frame) / line_cycles` (FM-1 SID counts from each call's start); `$D019` reads
    `$81` from the start of a VBI play call until the tune writes it, else `$00`; the other
    VIC registers read back what was last written to them (a 64-byte shadow).
  - CIA 1: timer A's latch (`$DC04`, `$DC05` writes) and its counter (reads, computed from
    the absolute cycle and the latch: FM-1 SID returns the latch); `$DC0D` reads `$81` at
    the start of a CIA play call until read, then `$00`; CIA 2's `$DD0D` reads `$00`. The
    other CIA registers read back what was last written (16 bytes each).
  - Colour RAM (`$D800-$DBFF`) is not kept: writes are dropped and reads return `$00`
    (a known limit, `docs/reference/psid.md`).
  - Everything outside the I/O page, and all of it while `$01` maps RAM, is RAM.
- **SID reads are real** (Task 5b's voice shadow): `$1B` OSC3 and `$1C` ENV3 from an exact
  copy of the chip's voices that the main loop clocks with the 6502 (the audio chip is a
  frame behind it, so it cannot answer); `$19` and `$1A` (the POTs) read `$FF`; every other
  register reads the bus's last value, which decays to 0 after reSIDfp's TTL (`SID.cpp`:
  `0x1d00` cycles on a 6581, `0xa2000` on an 8580), and every access leaves its value on
  the bus as reSIDfp's does. A 2SID tune has a shadow per chip.

### Look-ahead and the stamped writes (Tasks 5a, 8, 9)
- **The main loop runs the 6502 ahead of the audio** in slices of
  **`PSID_SLICE_CYCLES` = 1,500** 6502 cycles (Task 8 confirms the size against
  `PSID_SLICE_WORST`), while it is less than **`PSID_AHEAD_CYCLES` = 39,312** (two PAL
  frames) ahead of the chip's clock and the write ring has room for a slice's worst
  (`PSID_SLICE_CYCLES / 3 + 2` entries: a SID write takes at least 3 cycles). Ahead
  enough, it idles, and the passes go to everything else.
- **The write ring** is the interrupt's: 1,024 entries of a 32-bit cycle (the tune's
  running count) and a 16-bit chip-register-value (`chip << 13 | reg << 8 | value`);
  single producer (the main loop), single consumer (the interrupt), as `reg_ring` and the
  scope's ring are.
- **The interrupt places each write at its cycle.** Each chip keeps `C`, the cycles it has
  clocked since the tune's start. To place a write at cycle `X`: render whole samples while
  the next sample's cycles fit (`(cycle_frac_q16 + cycles_per_sample_q16) >> 16`, stepped,
  **no division in the interrupt**: libgcc's divide is flash code, which `ram_audio.rs`
  rejects), then `sid_advance(chip, X - C)` clocks the voices the rest of the way into the
  next sample and takes those cycles off it (`cycle_frac_q16 -= k << 16`, which the next
  sample's add brings back positive since `k` is less than its cycles), then `sid_write`.
  The render loop itself is untouched, so every golden and `sid_budget` stays as it is.
- **The split budget:** a block renders each chip in at most **`PSID_SPLITS` = 32 parts**
  (Task 8 sets the number from the measured split cost so that the worst block holds
  `PSID_ISR_WORST`); writes beyond that in a block are applied, in order, at the block's
  end, and counted as **late**. A write whose cycle the chip has already passed (the 6502
  fell behind) is applied at once and counted as late too. The audio never waits for the
  6502.
- **The audio starts** at the first block after the 6502 has run one period past init's
  start (or init returned), so a slow init plays out in real time from silence, as on a
  C64, and the screen and the controls stay live through it.
- **The tap:** each part renders through `render_part`, tapped while LIVE shows, as the
  song's split does; a short part writes one more scope point, which the phase-folded scope
  takes (`app/scope.h`).
- **Mutes act on the chip,** not on the tune's writes: the tune keeps every gate, so OSC3,
  ENV3, sync and ring modulation stay exact. A muted voice's output leaves the mix and the
  filter's input; its oscillator, envelope and the filter's DC load go on (Task 5a's mute
  mask, sent through `reg_ring` as a pseudo-register at a block's start). GLO's mutes and
  solos act on voice v of both chips in a 2SID tune.
- **The song and the `.sid` never run together.** Chip A plays one or the other; an audio
  mode (`AUDIO_SONG`, `AUDIO_PSID`) says which, and changes only at a block boundary after
  the outgoing player has stopped and the interrupt has acknowledged it.

### Memory (Task 9)
- The 6502's 64 KiB **is** `__song_region`: loading a tune overwrites the song in RAM.
- The interrupt's `.sid` state (the write ring, 6,144 bytes, and about 128 of state)
  overlays the song's interrupt state in `.song_noinit` (`song_transport` 3,964 and
  `song_shapes` 3,920: 7,884 bytes) as one union.
- The main loop's `.sid` state (the environment, about 400 bytes, and two voice shadows of
  about 640 each) overlays the song's work space in `.pool.song_noinit` (`song_space`,
  1,340 bytes) as one union, which grows by about 400 bytes: M3's main new RAM.
- **Before a tune loads over an unsaved song,** the browser asks (`SONG NOT SAVED`: SAVE
  saves it first, ALGORITHM pressed again discards it, HOME cancels). When the tune stops
  for good (another view's PLAY, a song loaded, HOME out of the browser with the tune
  stopped), the song comes back from the store (the last song opened, by name), or the
  empty song if it had none.

### The keys, chip B and the rest of the firmware while a tune plays (Task 9)
- A 1SID tune takes chip A as a song does (`keys_route_set_song(1)`): the keys play chip B
  with their own setup; KEYS A behaves as AUTO during a tune (no voice can be taken from a
  `.sid`); UI sounds play on chip B's spare voice as usual.
- A 2SID tune takes chip B as well: the keys and the UI sounds are silent (a toast once,
  `KEYS OFF: 2SID TUNE`), and chip B is prepared back to the keys' setup when the tune
  stops.
- The song views (STEP, TRACKER and its pages) show `SID PLAYING: STOP TO EDIT` and take no
  edits; SCENE's generative pieces follow the chip through the tap as with no song; RED
  MOON RITE's song hooks see no song and show its idle loop.
- MIDI: Start restarts the subtune, Stop stops, Continue resumes; clock, song position and
  program change are ignored while a tune plays; clock out sends nothing (a PSID has no
  tempo). The store defers erases while a tune plays, as during a song (the quiet rule).

### The browser and the transport (Task 11)
- **MENU's new item `SIDS`** opens the browser, a list of the store's `.sid` files by
  their 16-character store names at the font's own size, as the SONG view's directory is.
  SELECT moves, ALGORITHM pressed loads the tune and opens NOW PLAYING; an empty store says
  `NO TUNES: SEE MANUAL`.
- **NOW PLAYING:** the header's title at 2× (two lines), author and released at 1×,
  `SONG n/m` (ALGORITHM turned steps the subtune, restarting it), the time since the
  subtune started, `PAL`/`NTSC`, each chip's model, a `2SID` mark, the three voice lanes
  with GLO's mute and solo state (as TRACKER's header), and the overruns and late writes
  when not zero.
- **PLAY** (global) starts the loaded subtune from init, or stops it (a one-block fade of
  chip A, then its registers cleared); **EDIT held + PLAY** pauses and resumes (the 6502
  and chip A stand still; chip B and the keys go on). A paused or stopped tune keeps its
  place in the browser.
- **STATUS** gets the 6502's rows while a tune plays: 6502 cycles a second, the
  main-loop share they cost (Task 12's meter), overruns, late writes, the shadow on or off,
  dropped third-SID writes.

### How tunes reach the device (Task 10)
- `.sid` is store file type **`STORE_FILE_SID` = 2**; the store's `STORE_FILE_MAX`
  (65,536) caps a tune, which every PSID within the C64's memory fits (a larger file is
  refused, `TOO BIG`).
- **SysEx `PUT`** (M2e Task 5) carries it; the device checks the header's first 124 bytes
  when the first packet arrives (Task 4's parser) and answers `NAK` with the reason for an
  RSID, a MUS file or a broken header, before any byte is written.
- **`sidou-sysex sid FILE.sid...`** (the host library's CLI) writes one `.syx` per tune,
  one SysEx message per packet, named from the header's title (uppercase, SIDOU's
  character set, 16 characters, `~2` on a clash); the manual names the tools that send a
  `.syx` with a pause between messages (and over TRS, the protocol's unacknowledged
  `PUT`). **The CLI opens no MIDI port in M3** (the implementers may not, and the companion
  is where an acknowledged `PUT` belongs); a port sender is the user's decision, later.
- `STORE_KEYS_MAX` (48 small values and files together) limits how many tunes the store
  holds next to the settings and songs: about 30. M3 does not change the store's format;
  `PUT` answers `NAK FULL` when the keys run out.

### RSID: rejected politely in M3; a later plan if wanted
`docs/TODO.md` asks M3's plan to decide. **Recommendation: keep the polite rejection in M3**
(`RSID: NOT YET` at `PUT` and in the browser), and leave RSID to its own plan after M3,
if the user wants it then. Why:
- **The headroom no longer decides it.** Under the look-ahead, CIA, IRQ and NMI timing
  within a frame is simulated in 6502 time, so a digi's NMIs cost main-loop time (about 9
  instructions per 6502 cycle, like any code), not interrupt time; the interrupt only sees
  more stamped writes (an 8 kHz digi is about 160 a frame, well inside the ring and the
  split budget's late-write fallback).
- **What it needs is a second environment:** a cycle-scheduled CIA 1 and 2 (timers A and B,
  IRQ and NMI), VIC raster interrupts, the C64's power-on state, and a KERNAL: the real ROM
  is Commodore's and cannot ship, so SIDOU would write a small replacement (its IRQ and NMI
  entries, `$EA31`, the vectors). That is about as much code and test surface again as the
  PSID environment (an estimated 4-6 KB of flash, which M3's reserve does not have).
- **It has no oracle here:** m6502.h + `psid.c` play no RSID; checking one needs
  libsidplayfp (GPL-2.0-or-later, usable test-only like reSIDfp), a larger harness than
  M3's.
- **Its tunes would need the SID's digi path checked first:** every digi tune the study
  found was RSID, and whether SIDOU's core sounds `$D418` digis as reSIDfp does is not
  tested.
- **M3's design leaves the door open:** `cpu6502_run`'s cycle limit is already the event
  hook an interrupt scheduler needs, the I/O dispatch is one function, and RSID's refusal
  is one code.

So the RSID entry in `docs/TODO.md` becomes "decided for M3: rejected; a later plan
(CIA/VIC interrupts, a SIDOU KERNAL stub, libsidplayfp as the oracle; BASIC tunes refused)"
(Task 14).

  | flags bit 0 (MUS) | `PSID_E_MUS` |
  | load address 0: two more bytes in the file for it (`offset + 2 <= n`) | `PSID_E_HEADER` |
  | the data is at least one byte, and load + length `<= 0x10000` | `PSID_E_TOO_LONG` |
  | the data overlaps `$0000-$0001` (the 6510's port) | `PSID_E_LOAD` |
  | songs 1-256 | `PSID_E_HEADER` |
  | start song 0 or above songs: 1 (accepted) | |
  | init address 0: the load address (accepted) | |
  | second SID address invalid (v3+): no second SID (accepted, flagged) | |

### Task 5a: The SID core for stamped writes: `sid_advance`, the voice mute mask

**Files:** `core/sid/sid.c`, `sid.h`, `platform/fm1/app.ld` (`.text.sid_advance`),
`host/crates/sidou-tests/tests/sid_advance.rs` (new), `app/reg_ring.c`/`.h` (the mute's
pseudo-register).

**Spec:**
- `void sid_advance(sid* s, uint32_t k)`: clocks the voices `k` cycles (`clock_voices`) and
  takes them off the next sample (`cycle_frac_q16 -= k << 16`); `k` must be less than the
  next sample's cycles (`(cycle_frac_q16 + cycles_per_sample_q16) >> 16`), asserted in
  host builds. In RAMTEXT.
- `uint32_t sid_next_cycles(const sid* s)` (inline): the next sample's cycles.
- **The mute mask:** `sid_set_mute(sid* s, uint8_t mask)`. The render loop's voice test
  changes from "routed into the filter, else not (voice 3 and `$18` bit 7)" to two masks the
  chip keeps up to date at `$17`, `$18` and mute writes: `route_on = routing & ~mute` and
  `direct_off = mute | (mode_vol bit 7 ? 4 : 0)`. A muted voice adds nothing to the filter
  or the direct path; the 6581's `dc_in` keeps following the real routing; nothing else
  changes. With `mute == 0` the samples are bit for bit as before.
- `reg_ring`'s pseudo-register for the mute, as `fx_live_pseudo`'s are, so the main loop's
  mute reaches the chip at a block's start.

**Tests (TDD):**
- every golden unchanged (`golden.rs`, the reference tests) and `sid_budget.rs`'s numbers
  unchanged or lower (the report shows both);
- `sid_advance`: rendering n samples with a write at cycle X placed by advance-then-write
  equals, for the voices' state, `sid_clock` to X then the write then `sid_clock` on
  (outside hard sync, where `sid_clock` documents its own difference); the sample count of
  a block is unchanged by any number of advances; the Q16 accumulator never goes wrong
  across 10^6 random advances (property test);
- the mute: with voice v muted, the render equals, sample for sample, a test-only build of
  `sid.c` (`-DSID_TEST_ZERO_VOICE=v`) whose `voice_out` returns 0 for that voice, on both
  models; OSC3, ENV3 and the other voices' sync and ring modulation are unaffected by mutes
  (their states compared write by write).

**Docs:** `core/sid/sid.h` comments; decision record 0005's split render, a line on
`sid_advance`.

## Risks

- **Instructions are not cycles.** fm1-emu counts instructions; the 6502 and the shadow run
  from flash through the I-cache, whose misses fm1-emu does not model. The study's 1.3 % of
  the CPU could be several times that on the device; the main loop has room for it, and
  Task 12's rule decides on numbers.
- **The voice shadow's cost** is about the chip's own voice work (up to a few hundred
  instructions per 22 cycles at the combined-noise transient), so up to about 5 % of the
  CPU while a tune plays, for every tune, since a tune's first OSC3 or ENV3 read cannot be
  known in advance. If flash day finds it too dear, reading those two from the audio chip a
  frame late is the cheap alternative, at the price of tunes that wait on ENV3 (they would
  hang to the play cap). The user decides with the numbers.
- **Hard sync's stepping:** the shadow and the audio chip step the voices in different
  spans; `sid_clock` documents the difference in what a synced voice did earlier in a step.
  OSC3 reads right after a sync may differ by that; the reSIDfp test lists the cases.
- **The second core:** M3 runs on one core. If a later pass moves the 6502 or chip B to
  the second core with Felucca's dual-core code, it takes a revision with Felucca's
  mailbox synchronisation issue (#267, open on 2026-10-21) fixed, or reviews the mailbox
  first; never 1.6.1's as it is.
- **The decoder:** the 6-byte compare-and-branch decodes at 7ca5b96 only through fm1-core's
  fallback, which fits "only the corpus offsets" by its own comment; a new compiler idiom
  in the dispatch can stop the emulator. Task 2 catches it at build time on the bench image.
- **M2 does not fit its own flash ceiling** without the win-back (Before M3, item 5), so
  M3's flash depends on the user's choice of levers, above all option 2 (the goldens move).
- **The store's 48 keys** limit the library to about 30 tunes next to the settings and
  songs; a store format change is out of M3.
- **SysEx `PUT` from generic tools over USB** depends on the tool's pause between messages;
  the acknowledged path is the companion's (Live Link), not M3's.
- **Overlaying the song:** every reader of the song's state must check the audio mode; one
  that does not reads a `.sid`'s ring as a song. Task 9's switch test and the song views'
  `SID PLAYING` cover the known readers; a later reader must use the mode check.
- **PSID tunes that expect ROMs** (BASIC or KERNAL routines and tables, colour RAM as
  storage) play wrongly; they are rare in PSID and listed as limits, not detected.
- **The digi path:** PSID tunes with PlaySID samples play without them; whether SIDOU's 6581
  sounds `$D418` digis as reSIDfp does is untested, and matters for a later RSID plan.
