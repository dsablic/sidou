# 0008: M3's 6502 is SIDOU's own; what SIDOU takes from FM-1 SID

**Status:** accepted, 2026-10-18 (the user: "let's adopt what makes sense from fm1-sid").

<!-- REUSE-IgnoreStart -->

## Context

M3 plays `.sid` files, so SIDOU needs a 6502 and a PSID environment on the FM-1. FM-1 SID
(Joakim Eriksson, `fm1-sid/` in fm1-emu) already plays PSID tunes in fm1-emu, not yet on a
real FM-1. A study on 2026-10-18 compared its 6502 with a SIDOU-native prototype on
fm1-emu, using 20 tunes and Tom Harte's tests.

m6502.h is slower by design: it ticks one cycle at a time and models the bus pins, which
buys accuracy and simplicity, not speed. These numbers count instructions; the FM-1's real
cycles are measured on flash day (risks below).

## Decision

**SIDOU writes its own 6502** (`core/cpu6502/`, GPL-3.0-or-later, from the prototype),
instruction-stepped with exact cycle counts.

**Scheduling: one frame of look-ahead.** The 6502 runs a whole player frame (init or play)
ahead in the main loop, or in small slices, and each SID write carries the 6502 cycle it
happened at. The audio ISR applies the writes at those cycles while rendering, so timing
stays exact within the frame. This replaces the old plan of fitting the 6502 into the ~185
instructions a sample left in the ISR (`docs/TODO.md`, "The 6502 must fit the audio
headroom"): at about 76 a sample of main-loop time, the 6502 costs about 1.3 % of the CPU.

**No second core.** Some FM-1 units misread memory on core 1, and the community's
dual-core code is GPL-3.0-only. Neither is needed.

**The rule for anything taken from FM-1 SID: ideas, checked and improved, never copied
blindly.** Each piece is checked against the PSID file spec (HVSC's `SID_file_format.txt`)
and the real C64's behaviour, and is improved where SIDOU can do better. FM-1 SID's own
behaviour is never the reference. When the host oracle disagrees with SIDOU, the spec and
the C64 decide, and FM-1 SID's player can be the side that is wrong.

**What SIDOU takes from FM-1 SID:**

1. **The PSID environment's design** from `psid.c` (BSD-2-Clause): the header parse, the
   init and play calls through a trampoline with a cycle limit, the CIA-timer period,
   the bank register at `$01`. Where SIDOU's code follows it closely, the file keeps
   Joakim Eriksson's BSD-2-Clause notice beside SIDOU's (REUSE, `LICENSES/BSD-2-Clause.txt`),
   and the design doc's section 11 lists it. SIDOU's version fixes what the study found:
   - **Bounds:** the data offset and the load address come from the file and are used
     unchecked (`psid.c` around line 145): with a crafted 124-byte file, or a data offset
     beyond the file's end, the loader reads past its buffer. Every header field is
     checked against the file's length first.
   - **Raster:** an absolute raster position from the frame's cycle, not a counter.
   - **CIA periods under 1,000 cycles** are honoured (FM-1 SID drops them to the frame).
   - **The speed bit** for songs above 32 uses bit 31, as the PSID spec says.
   - **Second-SID tunes** (PSID v3/v4 addresses) go to chip B.
   - **Voice 3's OSC3 and ENV3** are read from a shadow the audio side updates, so
     tunes that read them still work under look-ahead.

   Beyond those fixes, SIDOU improves on it where its player simplifies:
   - **NTSC tunes** run at the NTSC clock and frame (1,022,727 Hz, 263 lines of 65
     cycles), from the header's clock flags. FM-1 SID plays everything as PAL, so NTSC
     tunes run about 17 % slow.
   - **The chip model:** "8580" or "6581" in the header picks the chip's profile. When
     the header says "unknown" or "either", the user's chip choice is used instead of
     falling back to the 6581.
   - **Init without a stall:** FM-1 SID runs init in one blocking call of up to 5 seconds
     of 6502 time. SIDOU runs it in slices, so the screen and the controls stay live
     while a tune with a long init loads.
   - **Overruns are reported:** a play call that runs past its cycle limit is counted and
     shown in STATUS, not cut off silently.
   - **SID reads:** FM-1 SID returns a pseudo-random byte for OSC3 and 0 for every other
     register, ENV3 included. SIDOU returns voice 3's real OSC3 and ENV3 (the shadow
     above), the POTs, and for the write-only registers the last value written, fading
     as the real chip's bus does.
2. **The write-stamped look-ahead** scheme, as above.
3. **A host-side oracle.** m6502.h (zlib) with `psid.c` and `psidlog.c` (BSD-2-Clause)
   go in a host test crate only, never in the firmware. The tests compare SIDOU's
   cycle-stamped SID write stream against theirs, tune by tune, beside Tom Harte's and
   Klaus Dormann's tests. Each known difference (the fixes and improvements above) is
   listed as expected, so any other difference fails. `LICENSES/Zlib.txt` is added with them.
4. **Reporting the loader's bounds bug upstream** with a minimal file. The user reviews
   the issue before it is posted.

**What SIDOU does not take:**

- `fm1-sid/firmware/*` (GPL-3.0-only): taking it would make the combination
  GPL-3.0-only.
- reSID: SIDOU has its own SID core (decision records 0002 and 0003).
- The dual-core start-up.

## Built (M3, as of 2026-10-25)

SIDOU's own 6502 (`core/cpu6502`) and PSID environment (`core/psid`) play `.sid` tunes with the
look-ahead as decided, in the main loop; the audio interrupt places the stamped writes.

| | Measured (fm1-emu, instructions) |
|---|---|
| The 6502, per 6502 cycle | 8.4 to 8.9 on GoatTracker tunes (`CPU6502_INSTR_PER_CYCLE` 9.33, the worst workload plus 5 %) |
| The dearest main-loop pass (a slice) | 33,269 (`PSID_SLICE_WORST` 40,000): two chips, noise combined, an OSC3 read every 4 cycles |
| The audio interrupt's `.sid` path | at most 55.1 a sample on the corpus; 105.0 at a write every 4 cycles (`PSID_ISR_WORST` 120) |
| The audio block with two chips | 1,658.5 a sample (`AUDIO_TARGET` 2,700) |
| The busiest main-loop pass | 101,832 with LIVE showing (`POLL_INSTRUCTIONS` 120,000) |
| The image | 526,192 bytes, 7,808 under M3's 534,000 |
| RAMTEXT | 48,736 of 49,152 (416 free), after main's v0.4.0 merged |
| RAM (`.bss`) | the tune's state shares the song's memory; M3's `.bss` grew by about 470 bytes (176 for the player, 16 for the store, 260 for the views, 16 for the meter) |
| The meter (Task 12, TIMER4) | the dojo tune in fm1-emu: 1.2 % of the CPU, 296 ticks a thousand 6502 cycles |

The study's 1.3 % of the CPU is the figure to compare. **The flash day (2026-10-25,
[results](../hardware-results/2026-10-25-m3-flash-day.md)):** the unit reads 2.3-2.5 times
fm1-emu's share on every tune, at worst 10-12 % (Sound Test), under section 21's 15 %; the late
writes are the same in fm1-emu (a block's 15 render parts, not the device's speed), so no
fallback was taken and M3 shipped as built.

## Risks

- **Instructions are not cycles.** fm1-emu counts instructions; the 6502's real cost on
  the FM-1 is measured on the first flash day after Task 1.
- **fm1-emu's decoder gap at the pinned `e52f464`:** the compiler emits a 6-byte compare
  and branch (`43 ff …`) in the 6502's dispatch that the pinned emulator cannot decode.
  The fm1-emu bump should fix it; otherwise the core is compiled to avoid it.
- **OSC3 and ENV3 under look-ahead** are a frame stale unless the shadow is updated per
  write. Tunes that read them are checked by ear and by the oracle.
- **RSID and digis are untested:** every digi tune found was RSID, which section 5
  rejects. `docs/TODO.md`, "Decide on RSID playback", stays open for M3's plan, now with
  the look-ahead's spare time measured.
- **Memory:** the 6502's 64 KB overlays the song's content region (M2 overview). Only the
  in-ISR variant would need fast RAM, and it is not planned.

## Effort

About 4-6 well-specified tasks, around 1,200 lines with tests: the core with Harte and
Dormann tests; the PSID environment with the fixes; the look-ahead and stamped writes in
the audio path; the host oracle; the second-SID and voice-3 handling; the device
measurement.
